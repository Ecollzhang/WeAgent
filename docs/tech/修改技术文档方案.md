# WeAgent 技术文档修改方案

## 1. 需求理解

本次不是直接修改 `WeAgent技术文档.md`，而是先形成一份明确的修改方案。目标是把技术文档从偏功能说明的文档，调整为更贴近真实代码实现、技术链路清晰、模块边界准确的技术文档。

重点要求：

- 系统架构要写清楚，能准确反映 Web / Desktop / Android、Flask 后端、Socket.IO、Docker 沙箱、Orchestrator、Provider Runner、数据库之间的关系。
- 核心模块要贴合真实代码结构，不能写成虚构模块。
- 核心技术实现要写扎实，突出 WeAgent 的技术亮点。
- 多类型产物不能简单写成 Artifact 表统一存储，要反映真实的 `Message.elements`、sandbox event、容器文件、前端工作台共同组成的机制。
- 多 Agent 协作、工作流调度、Adapter、沙箱容器、事件与产物上报、能力投影等都要写清楚。
- 修改过程分阶段完成，每阶段有任务、验收标准和验证方式。

## 2. 当前技术文档存在的问题

### 2.1 产物系统描述不准确

当前文档容易让读者理解为所有产物都由 `Artifact` 表统一管理，但真实实现不是这样。

真实情况：

- `Artifact` 模型目前只覆盖 `code/webpage/document/ppt/diff` 这类传统产物。
- 大量消息产物实际存在于 `Message.elements`、`Message.raw_output`、sandbox event、前端 artifact element 中。
- `table/image/file/service/workflow` 等类型主要由 `sandbox_event_bridge.py` 转成消息元素，再由前端 `MessageBubble`、`ArtifactWorkbench` 渲染。
- 表格产物不一定存在于容器目录，可能直接使用内置 `columns/rows`。
- workflow 不是普通文件产物，而是工作流数据结构。

修改方向：

- 把“产物系统”改成“消息元素 + Artifact 表 + 容器文件 + 前端工作台”的组合机制。
- 明确 `Artifact` 表不是所有产物的唯一来源。
- 单独说明 `Message.elements` 在多类型产物展示中的作用。

### 2.2 Agent 执行链路过于简化

当前文档只写了“发送消息 -> Agent 执行 -> 返回结果”，但真实实现更复杂。

真实情况：

- `message_service.send_message()` 保存用户消息。
- 用户消息触发后台线程 `_dispatch_agent_sandbox()`。
- 后端创建 Agent 占位消息。
- 后端创建 `AgentRun`。
- 沙箱事件通过 `sandbox_event_bridge` 持续更新 Agent 消息。
- `AgentRun.last_seq` 用于事件序号和去重。
- 最终消息状态通过 `conversation_message_status`、`conversation_message_element_stream` 等事件推送。

修改方向：

- 把 Agent 执行链路细化为：用户消息、占位 Agent 消息、AgentRun、sandbox send、事件回传、消息更新。
- 强调同步返回不是主要结果来源，真实流式更新来自 sandbox event。

### 2.3 多 Agent 协作和工作流调度不够贴合实现

当前文档写了主持人 Agent 和 worker Agent，但没有写真实的主持人 plan 解析、workflow 生成、用户选择工作流等细节。

真实情况：

- 多 Agent 由 `message_service.py` 中的主持人逻辑驱动。
- 主持人会生成 `plan/answer` 类型结构。
- plan 会被转换为 workflow element。
- 前端 `ChatWindow` / Desktop `Conversations` 有工作流编辑、保存、选择、预览能力。
- 用户选择的 workflow 会随消息发送给后端，并写入 message meta。
- 工作流不应该被当成普通 `moderator-plan.json` 文件展示。

修改方向：

- 在核心技术实现中强化“多 Agent 协作与工作流调度”。
- 写清楚主持人计划、worker 调度、workflow 生成、workflow 预览、workflow JSON 复制的关系。
- 写清楚 workflow 在消息展示和用户选择中的前后端流转。

### 2.4 Adapter 适配器实现不够完整

当前文档写了 `ProviderRunnerFactory`，但缺少关键实现点。

真实情况：

- `AgentRuntime` 内部根据 `provider_name` 创建 Provider Runner。
- `ProviderRunnerFactory` 映射 `claude/claude_code/codex/opencode`。
- `ClaudeCodeRunner`、`CodexRunner`、`OpenCodeRunner` 都继承统一 Runner 接口。
- Runner 负责：
  - build command
  - provider env
  - resume marker
  - auth error 判断
  - stdout/stderr 解析
  - timeout 控制
- 容器内有 `provider_health.py` 和 `/api/providers` 用于检测 CLI 可用性。
- Codex 还有 relay、`CODEX_AUTH_JSON`、`CODEX_CONFIG_TOML` 等处理。

修改方向：

- Adapter 章节从“支持三个 Provider”升级为“统一 Runner 生命周期”。
- 加入 Provider Health、resume、环境变量映射、错误标准化。
- 区分 Agent Adapter 和工具 Provider Config，避免概念混淆。

### 2.5 沙箱容器机制缺少真实路由和文件代理细节

当前文档写了沙箱，但还不够具体。

真实情况：

- 宿主侧 `/api/sandbox` 代理容器内 `/api/*`。
- 容器内 server 监听 8080。
- 容器工作区是 `/workspace`。
- Agent 私有目录是 `/workspace/agents/<workspace_name>`。
- 共享目录是 `/workspace/shared`。
- session 数据在 `/workspace/.session`。
- HTML 预览会通过 `_inject_html_base()` 和 `_rewrite_workspace_css()` 修正资源路径。
- `ServiceManager` 会为 Vite 服务自动补 `--base`。
- 文件写入走 `/files/write`，会触发 workspace diff。

修改方向：

- 把沙箱章节写成“宿主代理层 + 容器服务层 + 工作区文件系统 + 服务代理”。
- 补上 HTML/CSS 路径重写。
- 补上文件写入和 diff 捕获链路。

### 2.6 多类型产物预览与编辑需要强调前端工作台

当前文档提到了产物适配，但没有充分体现这是 WeAgent 的核心技术亮点。

真实情况：

- Web 端有 `ArtifactWorkbench`。
- 支持：
  - `CodeEditor`
  - `HtmlPageEditor`
  - `ImageCropper`
  - `DiffViewCard`
  - table inline edit
- 图片、表格、代码、HTML、Diff 的编辑方式不同。
- 表格编辑会写回 CSV。
- 图片裁剪会生成 base64，并通过 `writeFile` 写回容器文件。
- HTML 编辑器会清理编辑器注入痕迹再写回。
- Diff 可以作为旁栏辅助查看。

修改方向：

- 把“多类型产物预览与编辑适配”单独写成核心亮点。
- 按类型说明预览方式、编辑方式、保存方式。
- 明确 Web 和 Desktop 都有工作台能力，Android 只保留主要查看能力。

### 2.7 工具集 / 能力系统写得太弱

当前文档只是提到 Toolset / Capability，但真实实现很多。

真实情况：

- 有 `capability_controller.py`。
- 有 capability import preview / confirm / security audit。
- 有 npx / MCP / markdown skill 导入。
- 容器内有 `.weagent` projection。
- `McpRuntime` 支持 manifest 声明的 MCP server。
- 工具 Provider Config 可以绑定 http/model/database 等 provider。
- 工具调用记录可以同步回后端。

修改方向：

- 在核心模块或核心技术中新增“能力与工具投影机制”。
- 说明后端管理能力，运行时投影到容器 `.weagent`，Agent 通过工具注册表和 MCP runtime 使用。

### 2.8 关键接口和数据模型需要按真实实现修正

当前接口和模型有些偏泛化。

需要修正：

- `Message` 要补充：
  - `elements`
  - `raw_output`
  - `run_id`
  - `artifact_id`
- `Artifact` 要说明是旧式 / 独立 artifact，不等同于所有消息产物。
- `Conversation` 要保留：
  - `sandbox_session_id`
  - `sandbox_container_id`
  - `sandbox_host_port`
  - `sandbox_status`
  - `is_favorite`
- `Agent` 字段里应使用真实字段倾向：
  - `adapter_name`
  - `capabilities`
  - `skill`
  - `system_prompt`
- 沙箱接口要补：
  - `/api/sandbox/events`
  - `/files/write`
  - `/workspace/<path>`
  - `/services/start`
  - `/services/<id>/logs`
  - `/mcp/...`
  - `/providers`

### 2.9 前端模块划分需要更贴近真实代码

当前写法较抽象。

建议按真实实现写：

- `Dashboard.vue`：Web 会话主入口和工作台协调。
- `ChatWindow/index.vue`：会话详情、侧栏、工作流、会话级配置。
- `MessageBubble/index.vue`：消息元素渲染。
- `ArtifactWorkbench/index.vue`：多类型产物工作台。
- `HtmlPageEditor` / `CodeEditor` / `ImageCropper` / `DiffViewCard`：具体编辑器。
- Desktop：
  - `clients/desktop/src/views/Conversations.vue`
  - `clients/desktop/src/components/MessageBubble.vue`
  - desktop sandbox service 封装。
- Android：主要功能迁移，不写成完整同构。

### 2.10 常见故障可以结合真实踩坑补充

建议补充：

## 4. 系统架构修改方案

系统架构要从简单链路改为真实分层架构。

本节写法：

- 先用一段文字说明 WeAgent 采用“多端客户端 + Flask 后端 + Docker 沙箱 + Provider Adapter + MySQL”的分层架构。
- 然后保留现有架构图或文字链路，不重新设计架构图。
- 再用表格说明每一层的职责、关键文件路径和通信方式。

应写清楚：

- 多端客户端：
  - Web：`frontend/`
  - Desktop：`clients/desktop/`
  - Android：`clients/android/`
- 前端请求层：
  - Axios REST API
  - Socket.IO Client
- 后端服务层：
  - Flask Controller
  - Service
  - Model / Repository
  - Socket.IO
- 沙箱宿主代理层：
  - `/api/sandbox`
  - Host Manager
  - 容器 session 管理
- Docker 容器层：
  - Container Server
  - Orchestrator
  - AgentRuntime
  - ProviderRunner
  - ToolRegistry
  - MCP Runtime
  - ServiceManager
- Provider 层：
  - Claude Code
  - Codex
  - OpenCode
- 数据层：
  - MySQL
  - Docker volume / `/workspace`

系统架构表建议包含：

| 层级 | 职责 | 关键实现 | 通信方式 |
| --- | --- | --- | --- |
| Web 前端 | 核心使用入口 | `frontend/` | REST API / Socket.IO |
| Desktop 端 | 桌面应用，连接外部后端 | `clients/desktop/` | REST API / Socket.IO |
| Android 端 | 移动端主要功能迁移 | `clients/android/` | REST API / WebView 网络 |
| Flask 后端 | 业务 API、Socket、数据库 | `backend/app/` | HTTP / Socket.IO |
| Sandbox Host | 宿主侧 Docker 管理与代理 | `backend/app/sandbox/host/`、`backend/app/sandbox/api/` | HTTP proxy |
| Container Runtime | 容器内 Agent 执行 | `backend/app/sandbox/container/` | Container API |
| Provider Adapter | 接入 Claude Code / Codex / OpenCode | `backend/app/sandbox/container/providers/` | CLI process |
| Data Layer | 业务数据与工作区文件 | MySQL、`/workspace` | ORM / Docker volume |

建议架构图文字：

```text
Web / Desktop / Android
        |
REST API + Socket.IO
        |
Flask Backend
        |
Sandbox Host Proxy
        |
Docker Sandbox Container
        |
Orchestrator
        |
AgentRuntime
        |
ProviderRunner
        |
Claude Code / Codex / OpenCode
```

验收标准：

- 能让读者一眼看懂请求、执行、事件、产物分别经过哪些层。
- 不再把沙箱写成一个模糊的 Docker 容器。
- 多端差异只写工程形态和通信差异，不展开 UI 功能。

## 6. 核心技术实现修改方案

核心技术实现建议作为全文最重要章节，拆成以下小节。

本节写法：

- 每个小节先用一段话说明该技术点解决什么问题。
- 再用流程图文本或表格说明实现链路。
- 最后列关键文件路径和边界条件。
- 篇幅优先级：沙箱容器、多类型产物、Adapter、多 Agent 工作流最高；能力 / 工具系统次之。

### 6.1 前后端通信与实时推送

要写：

- REST API 负责确定性操作。
- Socket.IO 负责实时事件。
- conversation room 隔离不同会话。
- 关键事件：
  - `conversation_message_created`
  - `conversation_message_status`
  - `conversation_message_element_stream`
  - `conversation_run_plan`
  - `sandbox_event`
- 容器事件通过 `/api/sandbox/events` 回到后端。

### 6.2 会话创建与沙箱绑定

要写：

- 创建 Conversation。
- 创建 sandbox session。
- 记录：
  - `sandbox_session_id`
  - `sandbox_container_id`
  - `sandbox_host_port`
  - `sandbox_status`
- 添加 Agent 到容器。
- 容器镜像依赖 `weagent-sandbox:latest`。

### 6.3 Agent 执行、事件与产物上报

要写：

- `message_service.send_message()` 保存用户消息。
- 后台线程触发 sandbox dispatch。
- 创建 Agent 占位消息。
- 创建 `AgentRun`。
- 容器执行过程中持续产生事件。
- `weagent-report` 不只上报进度，还上报：
  - progress
  - result
  - summary
  - table
  - image
  - code
  - file
  - service
  - error
- `sandbox_event_bridge` 负责转换事件并更新消息。
- `Message.elements` 是消息结构化展示核心。

### 6.4 多 Agent 协作与工作流调度

要写：

- 主持人 Agent 不是普通 worker。
- 主持人负责：
  - 分析任务
  - 读取成员能力
  - 生成 plan
  - 调度 worker
  - 汇总结果
- plan 可以转换成 workflow。
- workflow 在前端以卡片和图形方式展示。
- 用户也可以选择 / 编辑工作流，再随消息发送到后端。
- workflow 不是普通文件产物。

### 6.5 Adapter 适配器实现

要写：

- `ProviderRunnerFactory` 映射：
  - `claude / claude_code -> ClaudeCodeRunner`
  - `codex -> CodexRunner`
  - `opencode -> OpenCodeRunner`
- `AgentRuntime` 根据 `provider_name` 创建 Runner。
- Runner 负责：
  - `build_command`
  - env 注入
  - resume marker
  - stdout/stderr 解析
  - timeout
  - auth error
  - provider-specific config
- Provider health：
  - `/api/providers`
  - `provider_health.py`
- Codex 特有：
  - `CODEX_API_KEY`
  - `CODEX_AUTH_JSON`
  - `CODEX_CONFIG_TOML`
  - relay 处理
- OpenCode 特有：
  - `OPENCODE_API_KEY`
  - `OPENCODE_BASE_URL`
  - opencode config 生成

### 6.6 沙箱文件系统与服务代理

要写：

- `/workspace`
- `/workspace/agents/<workspace_name>`
- `/workspace/shared`
- `/workspace/.session`
- 文件树、raw file、download、write。
- HTML 预览：
  - `_inject_html_base`

  - `ServiceManager`

  - `/services/<id>/proxy/`

### 6.7 多类型产物预览与编辑适配

要写：

- 产物不是单一 Artifact 表。
- 真实来源：
  - `Message.elements`
  - `raw_output`
  - container file
  - sandbox event
  - workspace diff
  - 部分 Artifact 表
- 明确 `Artifact` 表不是所有产物的统一存储：
  - `Artifact` 表主要覆盖传统独立产物记录。
  - 大量运行时产物通过 `Message.elements`、`raw_output`、sandbox event 和前端 artifact element 展示。
  - 表格、workflow、service 等可能完全不依赖 `Artifact` 表。
- 前端适配：
  - file：raw file / workspace proxy
