- 先让读者知道项目是什么、包含哪些能力、本文覆盖哪些内容，再进入技术栈、架构、模块和实现机制。

- 标题尽量使用直观中文，专有名称放在正文首次出现时解释，不把 `Adapter`、`Provider Runner`、`Toolset`、`Glossary` 这类词直接作为标题。
- 每节先用一两句话说明“这一节在讲什么”，再给必要细节；不一上来堆表格。
- 模块部分可以使用表格、清单或短段落，但每个小模块都必须有一句话说明它解决什么问题。
- 相关代码只保留必要锚点，不把正文写成证据清单。
- 表格只用于降低理解成本；能用短段落讲清楚的内容，不强行表格化。
- 数据流时序图保持可读，每张图控制在 5 到 6 个参与者以内；超过时拆成多张图，不画全系统大图。
- 保留源文档的严谨性：不写代码之外无法确认的功能，不把分支和内部审计信息放到对外开头。

## 1. 项目与文档范围

本章回答“项目是什么、项目包含什么、本文讲什么、不讲什么”。这部分需要对外友好，避免出现分支名、提交号、内部事实矩阵等审计语言。

### 1.1 项目是什么

WeAgent 是面向 AI 协作任务的多端工作台。它把自然语言任务、多个可配置智能体（Agent）、工具能力、运行产物和服务预览放在同一个会话空间中，让用户可以像聊天一样发起任务，同时看到任务如何被拆解、执行，并沉淀为文件、页面、工作流或可预览服务。

### 1.2 项目包含哪些能力

本节用短段落说明项目能力边界，而不是写成宣传语。

建议覆盖：

- 多端客户端：Web、桌面端、Android。
- 会话式任务执行：消息、参与者、运行状态和实时进度。
- 可配置智能体：全局配置和会话级临时配置。
- 多角色协作：主持角色拆解任务，其他角色执行子任务。
- 工具能力管理：技能、工具、外部协议和插件按能力统一管理。
- 产物沉淀：代码、文件、网页、图片、差异、工作流和服务预览。
- 隔离执行：任务在容器边界内运行，后端负责协调和代理。

### 1.3 文档说明哪些内容

本文覆盖真实技术栈、系统架构、核心模块、关键实现机制、关键数据流、开发者运行与验证方式、关键接口与数据模型、已知限制、常见故障和术语说明。

### 1.4 文档不说明哪些内容

本文不写完整接口手册，不写完整数据库 ER 图，不承诺未在代码中确认的路线图功能，不把内部审查过程作为正文重点。

### 1.5 事实边界

正文以当前代码、配置、运行脚本、模型、路由、测试和已确认分支事实为准。内部事实源可保留在维护说明或附录中，不放在第一屏。

## 2. 相关技术栈

本章作为技术地图，帮助读者快速知道系统由哪些技术组成。它只做定位，不展开复杂机制。

### 2.1 客户端技术

说明 Web、桌面端、Android 分别使用什么技术，以及它们都连接同一个后端。

建议保留：

- Vue 2.7、Vue Router、Vuex、Element UI、Axios、Socket.IO Client。
- Electron Desktop。
- Capacitor Android。
- Web 是主功能基准，桌面端接近 Web，Android 承载移动端主流程。

### 2.2 服务端技术

说明后端为什么是系统控制面。

建议保留：

- Flask、Flask-SocketIO、SQLAlchemy、Flask-JWT-Extended、Flask-Migrate。
- MySQL、Redis。
- 后端承担认证、会话、消息、智能体、产物、能力、容器代理和实时推送。

### 2.3 执行环境技术

说明任务不是直接在后端进程里运行，而是在容器边界中运行。

建议保留：

- Docker Sandbox 在正文首次解释为“基于 Docker 的隔离执行环境”。
- Orchestrator 在正文首次解释为“容器内任务调度器”。
- AgentRuntime 在正文首次解释为“单个智能体的运行上下文”。
- Provider Runner 在正文首次解释为“连接外部执行引擎的运行器”。
- Claude Code、Codex、OpenCode。
- `weagent-report` 和 `weagent-service`。

### 2.4 数据与基础设施

说明系统运行依赖。

建议保留：

- MySQL 保存用户、智能体、会话、消息、产物和能力数据。
- Redis 作为后端辅助基础设施。
- Docker Desktop 负责本地容器运行。
- Node.js / npm 用于前端、桌面端、移动端构建。

## 3. 系统架构

本章回答“各层如何连在一起”。先给一张总览图，再按层说明职责。

### 3.1 总体架构

建议保留一张总览图或简洁链路：

```text
Web / Desktop / Android
        |
        | REST API / Socket.IO
        v
Flask Backend
        |
        | Sandbox Host Proxy
        v
Docker Sandbox
        |
        | Orchestrator / AgentRuntime
        v
Provider Runner
        |
        v
Claude Code / Codex / OpenCode
```

本节重点解释：客户端负责交互，后端负责协调，容器负责隔离执行，外部执行引擎负责完成具体 AI 任务。

### 3.2 客户端层

说明 Web、桌面端、Android 的共同点和差异。

重点表达：

- Web 是功能最完整的工作台。
- 桌面端通过 `serverUrl` 连接外部后端，适合桌面使用。
- Android 通过 Capacitor 承载移动端主流程，不写成完整桌面替代。

### 3.3 服务端层

说明后端是控制面。

重点表达：

- 处理登录、模型配置、会话、消息、智能体、产物、工具集和能力。
- 通过 REST API 处理确定性操作。
- 通过 Socket.IO 推送实时状态。
- 通过宿主侧代理管理容器会话。

### 3.4 隔离执行层

说明容器是执行边界。

重点表达：

- 一个正式智能体会话绑定一个 sandbox session。
- 容器内运行任务调度器和多个运行上下文。
- 运行上下文调用外部执行引擎运行器。
- 文件、日志、服务和产物事件都在容器内产生，再回传到后端。

### 3.5 外部能力适配层

说明系统如何统一不同执行引擎、工具协议和服务输出。

重点表达：

- Claude Code、Codex、OpenCode 的命令、认证和输出格式不同。
- 系统用统一运行器隐藏这些差异。
- 前端看到的是统一的消息、进度、产物和错误协议。

## 5. 核心技术实现

本章是 v2.0 的重点。它吸收参考文档的标题组织，但正文使用源文档中更完整的解释方式。标题尽量不用专有英文名，专有名词放在正文首次解释。

### 5.1 消息通信与实时推送

说明 REST API 和 Socket.IO 分工。

重点保留：

- REST API 处理登录、会话、消息、配置、文件、产物等确定性操作。
- Socket.IO 推送新消息、执行状态、步骤、产物元素和服务状态。
- 前端按会话更新消息状态，而不是只依赖一次性 HTTP 响应。

### 5.2 隔离执行机制

说明为什么需要容器执行边界，以及会话如何进入容器执行。

重点保留：

- 一会话一 sandbox session。
- 后端创建或恢复容器。
- 容器接口提供健康检查、任务执行、文件、工具、外部协议、服务和事件接口。
- 工作区保存智能体文件、能力投影和 session 状态。

### 5.3 外部执行引擎适配

说明系统如何把不同外部执行引擎统一成同一种运行协议。

重点保留：

- 智能体配置中保存适配类型。
- 运行器工厂选择 Claude Code、Codex 或 OpenCode。
- 运行器注入 API Key、Base URL、模型名和工作目录。
- 运行器统一 stdout、stderr 和错误结果。

### 5.4 任务执行、事件与产物上报

说明任务执行不是简单返回文本，而是一组结构化事件。

重点保留：

- 用户消息落库。
- 后端创建智能体占位消息和执行记录。
- 容器执行并产生事件。
- 事件桥接更新消息、执行记录和产物。
- 前端看到进度、Raw Output、产物卡片、服务入口和错误提示。

### 5.5 多角色协作与流程展示

说明多角色协作的核心是主持角色的任务拆解和执行调度，而不是多个角色同时聊天。

重点保留：

- 主持角色读取参与者、能力标签、技能和会话级配置。
- 主持角色生成任务计划。
- 其他角色执行子任务。
- workflow 作为消息元素展示，可预览、编辑、复制和本轮使用。
- 工作流图是调度上下文，不是全局配置。

### 5.6 工具能力管理

参考文档没有单独展开工具能力，但 v2.0 必须保留，因为这是项目的核心能力。

重点保留：

- Capability 统一 Skill、Tool、MCP、Plugin。
- Toolset 负责产品层分类和管理。
- AgentCapabilityBinding 记录智能体与能力的关系。
- 能力投影到 `/workspace/.weagent/*`，供容器内任务读取。
- 调用记录与安全审查作为可信执行的一部分。

### 5.7 多类型产物预览与编辑

说明系统如何把执行输出变成用户可查看、可编辑、可迁移的产物。

重点保留：

- Message elements 把输出拆成代码、文件、图片、表格、服务、Diff、工作流等类型。
- Artifact 保存代码、网页、文档、PPT、diff 等产物。
- Workbench 负责查看、编辑、比较和迁移。
- 文件迁移分为 preview 和 migrate 两步。
- 服务类产物进入服务预览链路，不混同为普通文件。

### 5.8 服务预览链路

说明容器内服务如何变成用户可打开的链接。

重点保留：

- 智能体在容器内启动开发服务。
- 服务管理器记录 `service_id`、端口、命令、状态和日志。
- 后端生成带 token 的 `proxy_url`。
- 前端展示服务卡片、日志、停止和重启入口。

### 5.9 会话级配置合并

说明会话级配置为什么重要，以及它和全局配置的边界。

重点保留：

- 会话级配置只影响当前会话。
- 可覆盖角色名、系统提示词、技能、启用状态等。
- 发送消息时进入 `agent_configs` payload。
- 后端生成调度上下文，不回写全局配置。

### 5.10 安全边界与错误处理

说明系统如何控制执行边界和失败反馈。

重点保留：

- Docker 隔离任务执行环境。
- 前端不直接访问容器文件系统。
- 文件访问通过容器 API。
- Provider 错误、容器错误、服务代理错误都要落到 Message / AgentRun / 前端状态。

## 8. 关键接口与数据模型
