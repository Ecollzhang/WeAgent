# WeAgent 智能研发（Smart R&D）领域服务设计方案

## 一、概述

基于 WeAgent 已有的 Agent 调度引擎、Docker 沙箱、多引擎适配、RAG 知识库等基础设施，为智能研发领域构建一个完整的 **AI 驱动研发管理平台**。围绕研发团队日常工作的四大核心模块——**项目管理**、**代码仓库**、**代码审查**、**构建管理**——提供从需求到交付的全流程 AI 协作能力。

### 四大核心模块


## 二、功能一：项目管理 (Project Management)

项目管理是研发工作台的核心入口，支持从项目创建到需求交付的完整生命周期管理。

### 2.1 项目 (Project)

项目是研发协作的顶层容器，一个项目对应一个软件产品/服务。

**功能清单**：

| 功能 | 说明 |
|------|------|
| 创建项目 | 填写项目名称、描述、技术栈（前端/后端/数据库/部署方式） |
| 项目列表 | 卡片网格展示，支持按工作空间筛选，显示项目状态、进度、成员数 |
| 项目仪表盘 | 项目概览：迭代进度、需求/Bug 统计、最近代码提交、构建状态 |
| 编辑项目 | 修改名称、描述、技术栈 |
| 归档项目 | 软删除，项目数据保留 |
| 项目上下文 | Agent 对话时自动注入项目信息（技术栈、当前迭代、成员等） |

### 2.2 迭代 / 冲刺 (Iteration / Sprint)

迭代是项目内的工作周期单元，组织该阶段需要完成的需求和修复的 Bug。

**数据模型**：

```sql
CREATE TABLE rd_iterations (
    id VARCHAR(36) PRIMARY KEY,
    project_id VARCHAR(36) NOT NULL,
    name VARCHAR(200) NOT NULL COMMENT '迭代名称，如 Sprint 1 / v1.0 发布',
    goal TEXT COMMENT '迭代目标',
    start_date DATE COMMENT '开始日期',
    end_date DATE COMMENT '结束日期',
    status ENUM('planning','active','completed','cancelled') DEFAULT 'planning',
    sort_order INT DEFAULT 0 COMMENT '排序序号',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (project_id) REFERENCES rd_projects(id) ON DELETE CASCADE,
    INDEX idx_project (project_id),
    INDEX idx_status (status)
);
```

**功能清单**：

| 功能 | 说明 |
|------|------|
| 创建迭代 | 填写名称、目标、起止日期 |
| 迭代列表 | 按时间线展示，支持「进行中/已完成/计划中」分类 |
| 迭代看板 | 三列看板视图（需求 / 进行中 / 已完成），拖拽更新状态 |
| 迭代详情 | 展示本迭代包含的需求列表 + Bug 列表，完成进度百分比 |
| 迭代统计 | 需求完成率、Bug 修复率、代码提交次数、构建通过率 |

### 2.3 需求 (Requirement)

需求是迭代中的开发任务单元，描述需要实现的功能。

**数据模型**：

```sql
CREATE TABLE rd_requirements (
    id VARCHAR(36) PRIMARY KEY,
    project_id VARCHAR(36) NOT NULL,
    iteration_id VARCHAR(36) COMMENT '所属迭代（可为空，表示待规划）',
    title VARCHAR(300) NOT NULL COMMENT '需求标题',
    description TEXT COMMENT '需求描述',
    priority ENUM('p0','p1','p2','p3') DEFAULT 'p2' COMMENT '优先级：p0紧急/p1高/p2中/p3低',
    status ENUM('backlog','todo','in_progress','in_review','done','closed') DEFAULT 'backlog',
    assignee_id VARCHAR(36) COMMENT '指派给谁',
    story_points INT DEFAULT 0 COMMENT '故事点',
    labels JSON COMMENT '标签（如：前端/后端/API/数据库）',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (project_id) REFERENCES rd_projects(id) ON DELETE CASCADE,
    FOREIGN KEY (iteration_id) REFERENCES rd_iterations(id) ON DELETE SET NULL,
    INDEX idx_project (project_id),
    INDEX idx_iteration (iteration_id),
    INDEX idx_assignee (assignee_id),
    INDEX idx_priority (priority),
    INDEX idx_status (status)
);
```

**功能清单**：

| 功能 | 说明 |
|------|------|
| 新建需求 | 标题、描述、优先级（P0-P3）、故事点、标签 |
| 需求列表 | 表格视图，按迭代/优先级/状态筛选排序 |
| 需求详情 | 展示完整信息 + 关联的 Git 分支 + 代码提交记录 |
| 分配开发者 | 指派给团队成员 |
| 拖入迭代 | 将 Backlog 中的需求拖入指定迭代 |
| 状态流转 | Backlog → Todo → In Progress → In Review → Done → Closed |
| 关联 Git 分支 | 从需求一键创建功能分支，自动关联 |
| 展示 Git 提交 | 需求详情页展示关联分支的所有 commit 记录 |

### 2.4 Bug 管理 (Bug Tracking)

Bug 是迭代中需要修复的缺陷，与需求并列为迭代的两大工作项。

**数据模型**：

```sql
CREATE TABLE rd_bugs (
    id VARCHAR(36) PRIMARY KEY,
    project_id VARCHAR(36) NOT NULL,
    iteration_id VARCHAR(36) COMMENT '所属迭代（可为空，表示待规划）',
    title VARCHAR(300) NOT NULL COMMENT 'Bug 标题',
    description TEXT COMMENT '复现步骤',
    expected_behavior TEXT COMMENT '期望行为',
    actual_behavior TEXT COMMENT '实际行为',
    severity ENUM('blocker','critical','major','minor','trivial') DEFAULT 'major',
    priority ENUM('p0','p1','p2','p3') DEFAULT 'p2',
    status ENUM('open','confirmed','in_progress','fixed','verified','closed','wont_fix') DEFAULT 'open',
    assignee_id VARCHAR(36) COMMENT '指派给谁',
    environment VARCHAR(500) COMMENT '环境信息（OS/浏览器/版本）',
    labels JSON COMMENT '标签（如：UI/后端/性能/安全）',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (project_id) REFERENCES rd_projects(id) ON DELETE CASCADE,
    FOREIGN KEY (iteration_id) REFERENCES rd_iterations(id) ON DELETE SET NULL,
    INDEX idx_project (project_id),
    INDEX idx_iteration (iteration_id),
    INDEX idx_assignee (assignee_id),
    INDEX idx_severity (severity),
    INDEX idx_status (status)
);
```

**功能清单**：

| 功能 | 说明 |
|------|------|
| 提交 Bug | 标题、复现步骤、期望/实际行为、严重程度、环境信息 |
| Bug 列表 | 表格视图，按严重程度（颜色标签）/优先级/状态筛选 |
| Bug 详情 | 完整信息 + 关联的修复分支 + 提交记录 + 修复验证 |
| 分配修复人 | 指派给开发者 |
| 拖入迭代 | 将 Bug 拖入指定迭代，和需求一起排期 |
| 状态流转 | Open → Confirmed → In Progress → Fixed → Verified → Closed |
| 关联 Git 分支 | 从 Bug 一键创建 fix 分支，自动关联 |
| 展示修复提交 | Bug 详情页展示修复分支的所有 commit |

### 2.5 Git 分支与提交关联

需求和 Bug 各自支持独立的 Git 分支管理和提交追溯。

**数据模型**：

```sql
-- 分支关联表（需求或 Bug 可关联多个 Git 分支）
CREATE TABLE rd_branches (
    id VARCHAR(36) PRIMARY KEY,
    project_id VARCHAR(36) NOT NULL,
    repo_id VARCHAR(36) COMMENT '所属代码仓库',
    branch_name VARCHAR(300) NOT NULL COMMENT '分支名称（如 feature/REQ-001-login）',
    source_type ENUM('requirement','bug') NOT NULL COMMENT '关联类型',
    source_id VARCHAR(36) NOT NULL COMMENT '需求ID 或 BugID',
    base_branch VARCHAR(300) DEFAULT 'main' COMMENT '基于哪个分支创建',
    status ENUM('active','merged','closed') DEFAULT 'active',
    created_by VARCHAR(36) COMMENT '创建者',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    merged_at DATETIME,
    INDEX idx_source (source_type, source_id),
    INDEX idx_repo (repo_id),
    INDEX idx_project (project_id)
);

-- Git 提交记录表（关联到分支）
CREATE TABLE rd_commits (
    id VARCHAR(36) PRIMARY KEY,
    branch_id VARCHAR(36) NOT NULL,
    repo_id VARCHAR(36),
    commit_hash VARCHAR(40) NOT NULL COMMENT 'Git commit SHA',
    author_name VARCHAR(200),
    author_email VARCHAR(200),
    message TEXT COMMENT '提交信息',
    files_changed INT DEFAULT 0 COMMENT '变更文件数',
    additions INT DEFAULT 0,
    deletions INT DEFAULT 0,
    committed_at DATETIME,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (branch_id) REFERENCES rd_branches(id) ON DELETE CASCADE,
    INDEX idx_branch (branch_id),
    INDEX idx_commit_hash (commit_hash)
);
```

**功能清单**：

| 功能 | 说明 |
|------|------|
| 创建分支 | 从需求/Bug 详情页一键创建 feature/fix 分支，命名自动生成（如 `feature/REQ-001`） |
| 分支列表 | 每个需求/Bug 下展示关联的所有分支及其状态 |
| 提交记录 | 展示分支下所有 commit 的列表（作者、时间、消息、变更量） |
| 提交详情 | 查看单次 commit 的变更文件列表和 diff |
| 合并状态 | 显示分支是否已合并到主分支 |
| Agent 辅助 | Agent 可根据需求描述自动生成分支名、commit message |

## 三、功能二：代码仓库 (Code Repository)

代码仓库模块提供 Git 仓库的管理、代码浏览和版本对比能力，与项目管理模块深度联动。

### 3.1 数据模型

```sql
-- 代码仓库表
CREATE TABLE rd_repos (
    id VARCHAR(36) PRIMARY KEY,
    project_id VARCHAR(36) NOT NULL,
    name VARCHAR(200) NOT NULL COMMENT '仓库名称',
    description TEXT,
    repo_url VARCHAR(1000) COMMENT '远程仓库地址',
    default_branch VARCHAR(200) DEFAULT 'main',
    language VARCHAR(50) COMMENT '主要语言',
    is_local TINYINT(1) DEFAULT 1 COMMENT '是否本地仓库（沙箱内）',
    status ENUM('active','archived') DEFAULT 'active',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    FOREIGN KEY (project_id) REFERENCES rd_projects(id) ON DELETE CASCADE,
    INDEX idx_project (project_id)
);

-- 代码目录/文件表（树形结构）
CREATE TABLE rd_repo_files (
    id VARCHAR(36) PRIMARY KEY,
    repo_id VARCHAR(36) NOT NULL,
    parent_id VARCHAR(36) COMMENT '父目录ID（null表示根目录）',
    name VARCHAR(500) NOT NULL COMMENT '文件/目录名',
    file_type ENUM('file','directory') NOT NULL,
    file_path VARCHAR(1000) NOT NULL COMMENT '相对路径',
    extension VARCHAR(50) COMMENT '文件扩展名',
    size BIGINT DEFAULT 0 COMMENT '文件大小(字节)',
    commit_hash VARCHAR(40) COMMENT '最新提交hash',
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (repo_id) REFERENCES rd_repos(id) ON DELETE CASCADE,
    INDEX idx_repo (repo_id),
    INDEX idx_parent (parent_id),
    INDEX idx_path (file_path)
);
```

### 3.2 功能清单

| 功能 | 说明 |
|------|------|
| 仓库列表 | 展示项目下所有代码仓库（名称、语言、默认分支、最近更新） |
| 代码目录浏览 | 树形文件浏览器，展开目录查看文件结构 |
| 文件内容查看 | 在线查看文件内容，支持语法高亮（highlight.js） |
| 分支列表 | 查看仓库所有分支（本地+远程），分支状态 |
| 分支切换 | 切换查看不同分支的代码目录 |
| 提交历史 | 查看仓库/分支的 commit 历史（图形化或列表形式） |
| 文件对比 (Diff) | 查看两次 commit 之间或分支之间的文件差异 |
| 文件搜索 | 在仓库中搜索文件名或代码内容 |
| Agent 生成代码自动入库 | Agent 在对话中生成的代码文件自动关联到对应仓库 |

### 3.3 与项目管理联动

- 需求/Bug 详情页直接跳转到关联分支的代码目录
- 提交记录追溯到对应的需求或 Bug
- 代码审查任务可直接选择仓库中的文件

## 四、功能三：代码审查 (Code Review)

多 Agent 并行审查，覆盖安全、规范、逻辑、性能四个维度，输出结构化审查报告。

### 4.1 审查流程

```
用户提交代码（从仓库选择 / 粘贴 / 上传）
  → 主持 Agent 制定审查计划
  → 4 个 Worker Agent 并行审查：
    ├─ 🔒 安全审查 Agent：OWASP Top 10、注入漏洞、认证缺陷、敏感信息泄露
    ├─ 📏 规范审查 Agent：命名规范、代码风格、设计模式、最佳实践
    ├─ 🧠 逻辑审查 Agent：边界条件、错误处理、空值检查、并发安全
    └─ ⚡ 性能审查 Agent：N+1 查询、内存泄漏、算法复杂度、资源释放
  → 主持 Agent 汇总
  → 结构化审查报告（评分 + 问题列表 + 修复建议）
```

### 4.2 数据模型

```sql
CREATE TABLE rd_reviews (
    id VARCHAR(36) PRIMARY KEY,
    project_id VARCHAR(36),
    repo_id VARCHAR(36) COMMENT '来源仓库',
    user_id VARCHAR(36) NOT NULL,
    title VARCHAR(300) NOT NULL,
    code_content LONGTEXT COMMENT '审查的代码内容（粘贴模式）',
    file_paths JSON COMMENT '审查的仓库文件路径列表（仓库模式）',
    language VARCHAR(50),
    status ENUM('pending','reviewing','completed','error') DEFAULT 'pending',
    summary TEXT COMMENT '审查总结',
    score DECIMAL(3,1) COMMENT '总评分 1-10',
    scores JSON COMMENT '{"security":8.5,"style":7.0,"logic":9.0,"performance":6.5}',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_project (project_id),
    INDEX idx_repo (repo_id),
    INDEX idx_user (user_id)
);

CREATE TABLE rd_review_issues (
    id INT AUTO_INCREMENT PRIMARY KEY,
    review_id VARCHAR(36) NOT NULL,
    severity ENUM('critical','warning','info') NOT NULL,
    category VARCHAR(50) NOT NULL COMMENT 'security/style/logic/performance',
    file_name VARCHAR(500),
    line_number INT,
    title VARCHAR(300) NOT NULL,
    description TEXT,
    suggestion TEXT COMMENT '修复建议',
    code_snippet TEXT COMMENT '问题代码片段',
    fixed_snippet TEXT COMMENT '建议的修复代码',
    FOREIGN KEY (review_id) REFERENCES rd_reviews(id) ON DELETE CASCADE,
    INDEX idx_review (review_id)
);
```

### 4.3 功能清单

| 功能 | 说明 |
|------|------|
| 创建审查 | 选择审查模式：粘贴代码 / 从仓库选择文件 / 选择 Commit |
| 审查列表 | 历史审查记录，按项目/状态/评分筛选 |
| 审查详情 | 总评分仪表盘 + 4 维度分别展示 + 问题卡片列表 |
| 问题卡片 | 严重级别颜色标签（红/黄/蓝）+ 代码片段高亮 + 修复建议 |
| 自动修复 | Agent 根据审查建议自动生成修复代码 |
| 审查评论 | 开发者可对每个问题进行回复（确认/质疑/忽略） |
| 审查统计 | 项目维度的审查频率、常犯问题类型分布 |

## 五、功能四：构建管理 (Build Management)

构建管理模块负责项目的构建、测试和部署流水线，与项目管理中的迭代关联。

### 5.1 数据模型

```sql
-- 构建任务表
CREATE TABLE rd_builds (
    id VARCHAR(36) PRIMARY KEY,
    project_id VARCHAR(36) NOT NULL,
    repo_id VARCHAR(36),
    branch_id VARCHAR(36),
    iteration_id VARCHAR(36) COMMENT '关联迭代',
    build_number INT NOT NULL COMMENT '构建序号（自动递增）',
    build_type ENUM('manual','push','schedule','mr') DEFAULT 'manual' COMMENT '触发方式',
    status ENUM('pending','running','success','failed','cancelled') DEFAULT 'pending',
    commit_hash VARCHAR(40) COMMENT '构建对应的commit',
    commit_message TEXT,
    started_at DATETIME,
    finished_at DATETIME,
    duration_seconds INT DEFAULT 0,
    log LONGTEXT COMMENT '构建日志',
    error_summary TEXT COMMENT '失败原因摘要',
    artifact_paths JSON COMMENT '构建产物路径列表',
    env_vars JSON COMMENT '构建环境变量',
    created_by VARCHAR(36),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (project_id) REFERENCES rd_projects(id) ON DELETE CASCADE,
    INDEX idx_project (project_id),
    INDEX idx_status (status),
    INDEX idx_iteration (iteration_id)
);

-- 构建步骤明细表
CREATE TABLE rd_build_steps (
    id INT AUTO_INCREMENT PRIMARY KEY,
    build_id VARCHAR(36) NOT NULL,
    step_name VARCHAR(200) NOT NULL COMMENT '步骤名称（install/lint/test/build/deploy）',
    step_order INT NOT NULL COMMENT '步骤序号',
    status ENUM('pending','running','success','failed','skipped') DEFAULT 'pending',
    command TEXT COMMENT '执行的命令',
    log LONGTEXT COMMENT '步骤日志',
    started_at DATETIME,
    finished_at DATETIME,
    duration_seconds INT DEFAULT 0,
    FOREIGN KEY (build_id) REFERENCES rd_builds(id) ON DELETE CASCADE,
    INDEX idx_build (build_id)
);
```

### 5.2 构建流水线

```
代码提交（Push / MR）
  → 触发构建
  → ┌─ Step 1: 环境准备（拉取代码、安装依赖）
  → ├─ Step 2: 代码检查（Lint、格式化）
  → ├─ Step 3: 单元测试（pytest / jest / go test）
  → ├─ Step 4: 构建打包（npm build / docker build / go build）
  → └─ Step 5: 部署（可选，部署到沙箱预览环境）
  → 构建完成通知（成功/失败 + 耗时 + 测试覆盖率）
```

### 5.3 功能清单

| 功能 | 说明 |
|------|------|
| 构建列表 | 展示所有构建记录（序号、状态、触发方式、分支、耗时） |
| 构建详情 | 展示每个步骤的执行状态、日志、耗时 |
| 触发构建 | 手动触发 / 代码推送自动触发 / 定时触发 |
| 构建日志 | 实时流式展示构建日志，支持搜索和下载 |
| 测试报告 | 展示测试通过率、覆盖率、失败用例详情 |
| 构建产物 | 生成的二进制/包/镜像/Dockerfile 等，支持下载 |
| 预览部署 | 构建成功后在沙箱中启动预览服务，生成可访问 URL |
| 失败通知 | 构建失败时通知相关开发者（含失败摘要） |
| 与迭代关联 | 迭代详情中展示该迭代的构建历史和质量趋势 |

## 六、全部数据模型总览

```
rd_projects (项目)
  ├── rd_iterations (迭代/冲刺)
  │     ├── rd_requirements (需求)
  │     │     └── rd_branches (分支) → rd_commits (提交)
  │     └── rd_bugs (Bug)
  │           └── rd_branches (分支) → rd_commits (提交)
  ├── rd_repos (代码仓库)
  │     ├── rd_repo_files (目录/文件)
  │     ├── rd_branches (分支) → rd_commits (提交)
  │     └── rd_reviews (代码审查) → rd_review_issues (审查问题)
```

## 十、演示流程："研发团队的一次完整迭代"

```
1. 项目经理创建项目"用户反馈系统"，选择技术栈 Vue 3 + Flask + MySQL + Docker
2. 创建 Sprint 1（2 周），设定迭代目标"用户反馈提交与展示"
3. 在 Sprint 1 中创建 3 个需求：
   - REQ-001: 反馈表单页面（P1, 指派给前端小张, 5 story points）
   - REQ-002: 反馈数据 API（P1, 指派给后端小李, 3 story points）
   - REQ-003: 管理员反馈列表（P2, 指派给前端小张, 3 story points）
4. 测试提交 2 个 Bug：
   - BUG-001: 反馈提交按钮在 Safari 下无响应（Critical, 指派给前端小张）
   - BUG-002: API 返回 500 当反馈内容超过 1000 字（Major, 指派给后端小李）
5. 前端小张从 REQ-001 创建分支 feature/REQ-001-feedback-form，开始开发
6. 后端小李从 REQ-002 创建分支 feature/REQ-002-feedback-api
7. 小张完成开发，提交代码 → 自动触发构建（lint → test → build）
8. 构建成功，生成预览 URL → 测试验证通过
9. 小张在仓库页面选择 REQ-001 相关文件 → 发起代码审查
10. 4 个 Agent 并行审查 → 返回结构化报告（总分 8.2，发现 1 个 critical + 3 个 warning + 2 个 info）
11. 小张根据审查建议修复问题 → 代码合并到 main
12. BUG-001 标记为 Fixed → 验证通过 → Closed
13. Sprint 1 结束时，迭代仪表盘显示：3/3 需求完成，2/2 Bug 修复，构建通过率 100%
```

## 十一、技术架构

同现有架构保持一致：

- **微服务**：RD 服务 (`:5101`) 独立 Flask 进程，通过主后端 (`:5002`) 代理转发
- **数据库**：MySQL `weagent_rd` 数据库
- **基座**：`DomainServiceBase` 提供 Flask + SQLAlchemy + JWT + Redis + CORS
- **前端**：Vue 2 + Element UI，Vuex 状态管理，Axios 请求代理
- **服务发现**：`/api/rd/spec` 自描述端点，Agent 通过 `call_service_api` 动态调用
- **沙箱集成**：构建任务在 Docker 沙箱中执行，Agent 通过工具调用操作项目/仓库/需求/Bug
