# AI\-Coding模式选择

本文档面向 Codex、Claude Code 等 AI coding agent。用户可以显式指定某一种 AI Coding 模式。AI 必须按用户指定的模式执行，但任何模式都不能覆盖项目的 Skill、Spec、Rules。

## 全局优先级

执行任何模式前，按以下优先级处理：

1. 用户最新明确指令

2. 数据安全和不破坏已有工作

3. 项目 Skill

4. 项目 Spec

5. 项目 Rules

6. 当前 AI Coding 模式

如果模式与 Skill / Spec / Rules 冲突，遵循 Skill / Spec / Rules，并说明冲突。

## 通用执行要求

无论用户选择哪种模式，AI 必须遵守

- 修改前先理解代码上下文。

- 不覆盖用户已有改动。

- 明确当前模式。

- 明确本轮目标和边界。

- 阶段完成时做直接验收测试。

- 可能影响已有功能时做回归测试。

- 无法自动化验证时给出人工验证清单。

- 进入下一个需求前，检查 git 未提交代码；建议用户先提交已完成且验证通过的功能，保持工作区和暂存区干净。

- 最终汇报必须包含改动、验证结果、风险和用户下一步动作。

## 模式 1：Vibe Coding 氛围编码

### 定义

以对话方式快速生成原型、代码草稿或方案草稿。该模式速度优先，不默认保证完整质量。

### 使用场景

- 原型验证

- UI 草稿

- 小工具

- 临时脚本

- 方案探索

- 不影响主系统的实验

### AI 执行方式

1. 快速理解用户意图。

2. 直接给出原型、草稿或最小实现。

3. 明确标注未完整验证的部分。

4. 如果要落到项目代码，说明影响范围。

5. 如果影响已有功能，补做必要回归测试。

### 用户触发示例

```Plain Text
使用 Vibe Coding 模式，先快速做一个原型。
```

### 输出要求

- 快速结果

- 简短说明

- 是否已验证

- 后续需要补的测试或规范

## 模式 2：Spec Coding 规约编码

### 定义

先写结构化需求，再实现。结构化需求必须包含用户故事、验收条件、范围、非目标、测试标准和待确认问题。

### 使用场景

- 正式需求

- 中大型功能

- 多端支持

- 跨模块改动

- 涉及接口、数据模型、权限、持久化的需求

### AI 执行方式

1. 复述需求。

2. 阅读相关代码。

3. 写结构化 Spec。

4. 列出确认问题。

5. 等用户确认或协商。

6. 按 Spec 分阶段实现。

7. 按验收条件和回归范围测试。

### 用户触发示例

```Plain Text
使用 Spec Coding 模式处理这个需求。
```

### 输出要求

- 需求复述

- 用户故事

- 验收条件

- 非目标

- 分阶段方案

- 测试方式

- 回归测试范围

- 待确认问题

## 模式 3：Test\-Driven AI Coding 测试驱动 AI 编码

### 定义

先生成测试或验证脚本，再生成满足测试的实现。

### 使用场景

- 后端服务逻辑

- schema 校验

- parser

- store mutation

- 数据转换

- 高回归风险 bug

- 可明确断言的业务规则

### AI 执行方式

1. 复述需求和预期行为。

2. 设计测试用例。

3. 优先写失败测试或最小验证脚本。

4. 实现功能。

5. 运行测试。

6. 根据测试结果修正。

7. 补充回归测试。

### 用户触发示例

```Plain Text
使用 Test-Driven AI Coding 模式。先写测试，再实现。
```

### 输出要求

- 测试计划

- 测试文件或验证脚本

- 实现改动

- 测试运行结果

- 回归测试结果

## 模式 4：Iterative Refinement 迭代精炼

### 定义

小步快跑，每次只改一个模块或一个主要问题，通过多轮反馈逐步精炼。

### 使用场景

- UI 调整

- 交互体验优化

- 复杂 bug 排查

- 多端视觉差异

- 实时状态和刷新状态不一致

- 用户需要频繁检查成果的任务

### AI 执行方式

1. 明确当前小步目标。

2. 只修改一个模块或一个主要问题。

3. 做局部验证和可能影响功能的回归测试。

4. 汇报本步结果。

5. 等用户检查后再继续。

6. 如果同类问题反复出现，回到根因分析。

### 用户触发示例

```Plain Text
使用 Iterative Refinement 模式。一次只修一个问题。
```

### 输出要求

- 当前小步目标

- 小范围改动

- 局部验证结果

- 回归测试结果

- 下一步建议

## 模式 5：Agentic Workflow 智能体工作流

### 定义

AI 作为自主 agent，负责规划、执行、检查、修正，并主动推进完整任务。

### 使用场景

- 目标明确的完整任务

- 多步骤工作

- 用户希望 AI 主动推进

- 需要代码阅读、实现、测试、修复一体化完成的任务

### AI 执行方式

1. 复述目标和边界。

2. 自主规划阶段。

3. 执行当前阶段。

4. 自主测试和检查。

5. 根据失败结果修正。

6. 汇报完成情况、验证结果和剩余风险。

### 用户触发示例

```Plain Text
使用 Agentic Workflow 模式。你自主规划、执行、测试和修正，但不要扩大到需求之外。
```

### 输出要求

- 自主计划

- 执行记录

- 测试结果

- 自动修正内容

- 未解决问题

- 需要用户决策的事项

## 模式切换规则

用户可以随时切换模式。

示例：

```Plain Text
从 Vibe Coding 切到 Spec Coding，写正式方案。
```

```Plain Text
这个 bug 反复出现，切到 Test-Driven AI Coding。
```

```Plain Text
这部分 UI 用 Iterative Refinement，我检查后再继续。
```

AI 在模式切换时必须：

- 说明当前模式。

- 说明执行方式如何变化。

- 保留已有上下文和已完成结果。

- 不重复做已验证工作，除非新模式要求补测试或补 Spec。

## 阶段完成统一标准

不论使用哪种模式，阶段完成必须包含：

- 当前需求或阶段的直接验收测试。

- 可能受影响功能的回归测试。

- 实时状态和刷新后状态一致性验证。

- 跨端影响说明。

- 未验证内容和原因。

- git 状态提醒：如存在已完成但未提交的改动，建议用户先提交当前阶段，再开始下一个需求。

- 用户下一步需要执行的动作。
