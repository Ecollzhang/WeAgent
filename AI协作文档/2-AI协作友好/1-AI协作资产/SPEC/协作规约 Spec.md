# 协作规约 Spec

> 版本：v1\.0 \| 最后更新：2026\-06\-08 \| 来源：zsw/1\-协作规约Spec\-中文版\.md
> 
> 本文档定义我们协作时如何把需求转化为可执行、可测试、可验收的结构化规约。
> 
> 

---

## 1\. 核心思想

我们的协作方式接近 Spec Coding、Test\-Driven AI Coding 和 Iterative Refinement 的组合：

- 先把需求写清楚，再进入实现。

- 先定义验收标准，再判断实现是否完成。

- 优先设计测试，再写满足测试的代码。

- 小步推进，每次只处理一个阶段或一个模块。

- 用户检查阶段结果后，再进入下一阶段。

## 2\. 需求输入格式

用户可以用自然语言提出需求。AI 需要先将需求整理为结构化 spec。

标准 spec 包含：

- **背景**：为什么要做这个需求。

- **目标**：最终要达成什么效果。

- **范围**：本次要做什么、不做什么。

- **用户故事**：从用户视角描述功能。

- **验收条件**：什么情况下算完成。

- **测试标准**：如何证明它完成且没有明显回归。

- **约束条件**：平台、兼容性、性能、样式、数据、接口、部署等限制。

- **待确认问题**：实现前需要用户确认的关键问题。

## 3\. 用户故事格式

使用以下格式描述用户故事：

```Plain Text
作为 <用户角色>，
我希望 <完成某个动作或获得某种能力>，
以便 <达成某个目标或减少某个成本>。
```

示例：

```Plain Text
作为桌面端用户，
我希望点击产物抽屉中的表格产物时可以直接查看表格内容，
以便即使表格没有生成实体文件，也能检查结果。
```

## 4\. 验收条件格式

验收条件必须可观察、可测试，避免含糊描述。

推荐使用 Given / When / Then：

```Plain Text
Given 当前会话中存在一个表格产物，并且该产物没有文件路径
When 用户在产物抽屉中点击"查看"
Then 页面应打开内置预览弹窗
And 弹窗应根据产物内置 headers/rows 渲染表格
And 不应请求容器文件路径
```

## 5\. 阶段拆分格式

复杂需求必须拆成阶段。

每个阶段包含：

- 阶段目标

- 实现范围

- 影响文件或模块

- 验收条件

- 测试方式

- 风险和依赖

示例：

```Plain Text
阶段 1：后端接口兼容
目标：让发送消息接口接受会话级 agent_configs。
范围：message schema、message controller、message service。
验收标准：带 agent_configs 的请求不再返回 Unknown field。
测试方式：schema 单测或最小脚本验证；发送接口手动验证。
```

## 6\. 测试优先原则

在实现前，AI 需要先说明测试策略。

优先级：

1. 单元测试：适合纯函数、schema、parser、store mutation、helper。

2. 集成测试：适合接口、数据库、socket/event、跨模块流程。

3. 构建检查：适合前端、桌面端、移动端打包相关改动。

4. 人工验证清单：适合 UI、视觉、真机、复杂外部环境。

如果无法写自动化测试，必须说明原因，并提供明确人工验证步骤。

## 7\. 非目标

每个 spec 应明确非目标，避免范围膨胀。

示例：

- 本阶段不修改 Web 端样式。

- 本阶段不处理 Android。

- 本阶段只接通接口，不优化 UI。

- 本阶段不重构历史代码。

## 8\. 变更管理

如果实现过程中发现新问题：

- 先判断它是否阻塞当前阶段。

- 阻塞则更新当前阶段 spec。

- 不阻塞则记录为后续阶段或风险。

- 不把新问题偷偷并入当前阶段。

## 9\. 完成定义

一个阶段只有同时满足以下条件，才算完成：

- 实现与 spec 一致。

- 验收条件已验证。

- 相关测试或构建已运行。

- 已说明未覆盖风险。

- 用户已检查，或明确允许进入下一阶段。

## 自我迭代

> 版本：v1\.0 \| 最后更新：2026\-06\-08 \| 更新人：zsw
> 
> 

### 修改流程

1. 协作规约方式变化时，更新本文件

2. 在文件头部更新版本号和日期

3. 修改需至少两人 review 确认（规约影响全团队协作方式）

### 触发条件

- 发现需求输入格式不够完善

- 验收条件或测试标准需要补充

- 阶段拆分或变更管理流程优化

- 来自实际协作的反馈表明某条规约不适用
