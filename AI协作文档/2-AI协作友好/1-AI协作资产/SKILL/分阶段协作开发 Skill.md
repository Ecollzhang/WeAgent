# 分阶段协作开发 Skill

使用这个 skill 时，把软件开发任务作为一个分阶段协作流程处理，而不是一次性完成所有实现。

## 核心流程

1. 先复述需求，再设计或编码。

    - 用具体语言总结用户要做什么。

    - 标出可能影响的范围：后端、Web、桌面端、Android、测试、文档、数据模型、构建脚本、部署等。

    - 明确写出当前假设。

    - 在需求足够清楚、能够形成方案前，不直接开始实现。

2. 先写方案，再实现。

    - 把工作拆成多个阶段。

    - 每个阶段必须包含：

        - 阶段目标

        - 实现范围

        - 可能影响的文件或模块

        - 验收标准

        - 测试或验证方式

    - 在方案中列出需要用户确认的问题。

    - 尽量把问题集中起来，让用户可以一次性答复。

3. 只问有价值的问题。

    - 优先询问行为逻辑、优先级、平台范围、数据持久化、API 契约、兼容性、交互约束、测试环境。

    - 能通过阅读代码确认的问题，不要问用户。

    - 如果可以做安全假设，直接说明假设，并在用户确认方案后继续。

4. 一次只执行一个阶段。

    - 只实现当前已确认的阶段。

    - 改动保持在当前阶段范围内。

    - 不静默扩展到后续阶段。

    - 如果发现后续阶段依赖当前设计，先更新方案，再继续。

5. 每个阶段都要测试。

    - 行为可测试时，编写或更新聚焦测试。

    - 自动化测试不现实的时候，给出明确的人工验证清单。

    - 汇报完成前，运行相关测试或构建。

    - 测试失败或跳过时，说明原因。

6. 阶段完成后汇报。

    - 总结完成了什么。

    - 列出验证结果。

    - 说明剩余风险或未完成项。

    - 提醒用户在进入下一个需求前，先提交已完成且验证通过的功能，保持工作区和暂存区干净。

    - 请用户检查当前阶段成果。

    - 等待用户要求修正或进入下一阶段。

7. 先修正，再继续。

    - 用户反馈优先视为当前阶段任务。

    - 先修复不符合预期的问题。

    - 修复后重新运行阶段验证。

    - 当前阶段被接受或明确延期后，再进入下一阶段。

## 输出模板

### 需求复述

```Markdown
我理解你的需求是：

- ...
- ...

当前我会先确认这些点：

- ...

我的默认假设是：

- ...
```

### 分阶段方案

```Markdown
方案：

阶段 1：...
目标：...
范围：...
验收标准：...
测试方式：...

阶段 2：...
目标：...
范围：...
验收标准：...
测试方式：...

需要你确认：

1. ...
2. ...
```

### 阶段完成汇报

```Markdown
阶段 X 已完成。

改动：
- ...

验证：
- ...

Git 状态：
- 建议先提交本阶段已完成且验证通过的改动，保持工作区和暂存区干净，再进入下一个需求。

请检查这一阶段结果。确认后我再继续下一阶段；如果不符合预期，我先修正这一阶段。
```

## 执行规则

- 详细规划前，优先阅读代码。

- 如果发现情况变化，及时更新方案。

- 遵循项目已有约定，不随意创造新架构。

- 工作区有未提交改动时，保留用户已有改动。

- 开始新需求前，在可行时检查 git 状态，并建议用户先提交已完成的改动。

- 测试强度要和阶段风险匹配。

- 没有验证，不声称完成。

- 阶段实现完成不等于可以自动进入下一阶段；需要用户检查时，等待用户确认。

- 如果用户明确要求跳过方案或“直接实现”，遵循最新指令。

## 测试标准

每个阶段选择实际可行的最强验证方式：

- 纯逻辑、服务方法、reducer、schema、parser、helper：写单元测试。

- API 契约、持久化、socket/event 流、跨模块行为：写集成测试。

- 前端或打包改动：跑构建检查。

- UI 布局、视觉表现、平台相关行为、环境依赖流程：提供人工验证清单。

如果不适合写自动化测试，说明原因，并给出具体人工验证步骤。

## 协作契约

默认循环：

1. 用户提出需求。

2. Codex 复述需求。

3. Codex 提出分阶段方案和确认问题。

4. 用户答复或协商方案。

5. Codex 执行阶段 1。

6. Codex 测试阶段 1。

7. 用户检查阶段成果。

8. Codex 修正当前阶段，或进入阶段 2。

持续循环，直到所有阶段被验收，或用户改变方向。
