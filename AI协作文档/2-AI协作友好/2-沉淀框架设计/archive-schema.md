## 1\. 本文件的用途

##### 项目概况

WeAgent 是一个以 IM 聊天为核心交互方式的多 Agent 协作平台原型。用户像使用微信、飞书一样，通过新建对话、发送消息和 @Agent 的方式，与不同 AI Agent 协作完成网页、代码、文档、PPT 等产物。平台的核心能力包括：单聊与群聊、多会话并行、由 Orchestrator 进行任务拆解和分派、在聊天流中展示代码 Diff、网页预览卡片、部署状态卡片等富媒体结果。项目评分中，AI 协作能力 占 30%，重点考察是否沉淀出与 AI 协作相关的 Spec、Skill、Rules 等规范，而不仅仅是实现一个聊天界面。

##### 这个 schema 的核心目的

这套 schema 的核心目的，不是定义一个成熟项目的完整开发制度，而是为当前项目提供一套“聊天后归档与沉淀”的结构化方法。它用于指导项目成员在与 AI 完成一轮对话后，判断本轮内容应当如何记录、归档和升级：先将阶段性结果整理为 session，再按需要提炼为 archive，并进一步把稳定内容升级到 spec / skill / rules / summary 中。通过这套 schema，项目能够把零散对话逐步转化为可复用的 AI 协作资产，从而为比赛中 30% 的 AI 协作能力 提供清晰、可展示、可追溯的证据。

## 4\. 归档时先判断内容属于哪一类

对话结束后，不是所有内容都写到同一个文件里，而是先判断其归属。

当前采用：

* `session` 必有
* `archive` 按需升级

也就是说，只要一轮对话进行归档，就必须写一份`session`，若该轮内容具有较强长期复用价值时，才进一步加写一份`archive`。

对话内容的归属判断如下：

* 如果本轮主要沉淀的是 `一次协作过程和阶段性结果`，写入 `sessions/`
* 如果本轮主要沉淀的是 `任务目标、范围、验收标准`，写入 `spec/`
* 如果本轮主要沉淀的是 `某个 AI 角色的职责、输入输出、边界`，写入 `skills/`
* 如果本轮主要沉淀的是 `已结束对话中值得长期保留的提炼结果`，写入 `archive/`
* 如果本轮主要沉淀的是 `阶段性复盘和方法总结`，写入 `summaries/`
* 如果本轮主要沉淀的是 `多轮验证有效的固定做法`，补充到 `rules/`

换句话说：

* `spec` 是任务定义
* `skill` 是角色定义
* `session` 是单轮协作记录，偏过程，默认必有
* `archive` 是对已结束对话的归档提炼，偏长期复用，按需整理
* `summary` 是阶段总结
* `rules` 是稳定规则

## 5\. 文件命名规则

日志类文件统一使用：

`姓名-文件类型-v模版版本号-日期.md`

版本号=对应文件的模版的版本号
需检查是否有同名文件，若有则补后缀，不得覆盖、删除旧文件

这里的"日志类文件"包括：

* `sessions/` 下的协作记录
* `archive/` 下的对话归档
* `summaries/` 下的阶段总结

### 文件存放路径

所有归档文件统一存放在根目录下的 `2-沉淀产物/` 中，结构如下：

```
2-沉淀产物/
├── archive-schema.md          ← 本文件，归档规范
├── archive-registry.md        ← 成员注册表
├── archive-registry-template.md
├── README.md
├── sessions/                  ← 会话记录（基础归档）
│   └── {姓名}-session-v{版本}-{MM-DD}[-{序号}].md
├── archive/                   ← 归档记录（长期保留）
│   └── {姓名}-archive-v{版本}-{MM-DD}[-{序号}].md
├── spec/                      ← 规范定义
│   └── {主题名称}.md
├── skills/                    ← AI 技能定义
│   └── {角色名称}.md
├── rules/                     ← 固定规则
│   └── {规则名称}.md
└── summaries/                 ← 阶段总结
    └── {姓名}-summary-v{版本}-{MM-DD}[-{序号}].md
```

所有路径均相对于项目根目录 `E:\华南理工\研一\第二学期 2026.3.2-\3-竞赛\1-字节全栈挑战赛\`。

AI 读取文件时需使用完整路径，例如：
- `2-沉淀产物/sessions/zby-session-v1.1-05-28.md`
- `2-沉淀产物/archive/zby-archive-v1.0-05-24.md`
- `2-沉淀产物/rules/html-generation.md`

推荐日期格式统一使用：

`姓名-文件类型-v模版版本号-MM-DD.md`

示例：

* 参考 `archive-registry.md` 中的成员名称，例如 `zby-session-v1.0-05-22.md`
* 参考 `archive-registry.md` 中的成员名称，例如 `zby-archive-v1.1-05-22.md`
* 参考 `archive-registry.md` 中的成员名称，例如 `zby-summary-v1.0-05-22.md`

如果同一成员同一天需要写多个文件，可在后面补短后缀：

* `zby-session-v1.0-05-22-1.md`
* `zby-session-v1.0-05-22-2.md`

非日志类文件不强制使用该命名方式：

* `spec/` 下可按主题命名
* `skills/` 下可按角色命名

如果当前归档人不在 `archive-registry.md` 中，应终止归档，并在对话中提出 ： `archive-registry.md`缺少配置

## 6\. 模板使用说明

本目录已提供模板文件，归档时应优先参考模板填写，而不是自由发挥。

### 6.1 `spec/spec-template.md`

适用场景：

* 这一轮对话已经把某个任务讲清楚了
* 已经能明确目标、范围、输入输出和验收标准

使用结果：

* 生成新的任务定义文件

\---

### 6.2 `skills/skill-template.md`

适用场景：

* 多轮对话后，某个 AI 角色的职责已经比较稳定
* 已经可以明确它负责什么、不负责什么

使用结果：

* 生成新的角色能力文件

\---

### 6.3 `sessions/session-template.md`

适用场景：

* 需要记录一次具体协作过程
* 本轮对话已经形成阶段性结果
* 这是当前最优先、最基础的归档落点
* 当前采用过程型记录方式，重点保留讨论过程、错误探索、修正与收敛结果

命名要求：

* 文件名使用 `姓名-文件类型-v模版版本号-日期.md`

\---

### 6.4 `archive/archive-template.md`

适用场景：

* 某段对话已经结束
* 该轮 session 中存在值得长期保留、后续复用的内容
* 需要从原始聊天或 session 中进一步提炼有效内容

命名要求：

* 文件名使用 `姓名-文件类型-v模版版本号-日期.md`

\---

### 6.5 `summaries/summary-template.md`

适用场景：

* 需要对某一阶段做复盘
* 需要总结本阶段沉淀出的 AI 协作经验

命名要求：

* 文件名使用 `姓名-文件类型-v模版版本号-日期.md`

## 7\. 每次归档至少要提取什么

无论写入 `session`、`archive` 还是 `summary`，都不应只是复制聊天内容。

至少应提取：

* 本次记录范围
* 本轮主题
* 本轮背景与初始判断
* 讨论过程
* 当前收敛结果
* 未解决问题 / 后续建议
* 是否能升级为 `Spec / Skill / Rules`

也就是说，归档的重点是 `提炼`，不是 `转存`。

\---

## 8\. 从对话到规范的升级规则

一轮对话结束后，内容通常先进入 `session`，再视稳定程度决定是否升级到 `archive` 或其他正式规范。

推荐判断方式如下：

* 每次形成阶段性结果的对话，先放 `sessions/`
* 只有当 session 中存在长期复用价值时，再升级整理到 `archive/`
* 已经明确任务范围的内容，升级为 `spec/`
* 多次出现且边界稳定的角色职责，升级为 `skills/`
* 多轮验证有效的固定做法，补入 `rules/`
* 一段时间后的整体回顾，整理进 `summaries/`

因此：

* `session` 是每轮归档的基础记录
* `archive` 是从 `session` 中进一步提炼出的长期材料
* `spec/skill/rules/summary` 是更正式的项目资产

## 9\. 当前执行建议

本 schema 成文时，项目仍处于较早阶段，因此当时采用了下面的简化流程。
当前继续使用本规范时，仍可沿用该流程，但应结合最新 `spec/`、`session/`、`archive/` 与 `summary/` 文档判断是否需要调整。

1. 先完成与 AI 的对话。
2. 判断这轮内容是否已经形成可复用结果。
3. 若已形成结果，先写一份 `session`。
4. 再判断这份 `session` 是否值得进一步整理成 `archive`。
5. 再判断其中哪些部分值得升级为 `spec / skill / rules`。
6. 阶段结束后，再补 `summary`。

如果拿不准写到哪里，优先原则是：

* 先写 `session`
* 再决定是否需要 `archive`
* 最后再从 `session` 或 `archive` 升级出 `spec / skill / rules`

这样最稳，也最不容易漏内容。
