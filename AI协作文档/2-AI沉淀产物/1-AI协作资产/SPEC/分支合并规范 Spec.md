# 分支合并规范 Spec

本文档用于指导 Codex、Claude Code 等 AI coding agent 或人工协作者处理分支合并工作。重点不是“直接合并”，而是先确定目标分支引入的修改范围，定位潜在或实际冲突，说明冲突发生在哪里、为什么发生，并给出可执行的冲突解决方案。冲突不仅包括代码文本冲突，也包括功能冲突、业务语义冲突、接口契约冲突、数据兼容冲突和多端行为冲突。

## 核心原则

- 合并前必须保护当前已有工作。

- 当前工作区和暂存区应保持干净。

- 不在不了解目标分支改动的情况下直接合并。

- 不静默覆盖用户改动。

- 合并方案必须说明改动范围、代码冲突、功能冲突、冲突原因、解决策略和验证计划。

- 合并完成后必须做直接验证和受影响功能的回归测试。

## 合并前检查

执行分支合并前，必须先检查

1. 当前所在分支。

2. 当前工作区是否有未提交改动。

3. 当前暂存区是否有已暂存但未提交内容。

4. 当前分支是否落后远端。

5. 目标分支是否存在。

6. 目标分支是否需要先拉取最新内容。

建议命令：

```Bash
git status
git branch --show-current
git fetch --all --prune
git branch -a
```

如果存在未提交改动：

- 不直接合并。

- 建议用户先提交当前已完成且验证通过的功能。

- 如果改动尚未完成，建议用户先保存当前状态，例如提交到临时分支或明确说明是否允许 stash。

- 未经用户明确同意，不执行会丢失改动的命令。

## 修改范围分析

在制定合并方案前，必须分析目标分支相对当前分支引入了什么。分析目标是确定“改了哪里、影响什么、和当前分支可能在哪里发生代码冲突或功能冲突”。

至少确认：

- 新增、修改、删除了哪些文件。

- 是否涉及后端、Web、桌面端、Android、数据库、配置、文档、构建脚本。

- 是否修改 API 契约、数据结构、认证权限、持久化逻辑。

- 是否修改共享组件、公共样式、工具函数、状态管理。

- 是否引入新依赖或构建配置变化。

- 是否可能影响已有功能。

- 哪些文件当前分支也改过，存在重叠修改风险。

- 哪些改动属于同一业务逻辑链路，不能分开处理。

- 哪些功能行为和当前分支已有行为存在语义差异。

- 哪些接口、状态、权限、数据结构或 UI 交互虽然没有文本冲突，但可能产生功能冲突。

建议命令：

```Bash
git log --oneline --decorate 当前分支..目标分支
git diff --stat 当前分支...目标分支
git diff --name-status 当前分支...目标分支
git diff 当前分支...目标分支
```

如果目标分支较大，应先按模块归类改动，而不是一次性概括。

输出修改范围时，建议使用以下结构：

```Markdown
修改范围：
- 后端：...
- Web：...
- 桌面端：...
- Android：...
- 配置 / 构建：...
- 文档：...

重叠风险：
- 文件：...
- 原因：当前分支和目标分支都修改了 ...
```

## 冲突定位

合并前应尽量预判冲突；合并后如果出现冲突，必须明确告诉用户冲突在哪里。这里的冲突包括代码冲突和功能冲突。即使 `git merge` 没有报冲突，也必须检查是否存在功能层面的不一致。

冲突定位至少包含：

- 冲突文件路径。

- 冲突所在模块或功能。

- 冲突类型。

- 双方分别改了什么。

- 为什么不能直接选择其中一边。

- 是否存在没有文本冲突但有功能冲突的情况。

常见冲突类型：

- 同一文件同一区域文本冲突。

- 同一接口或数据结构被双方以不同方式修改。

- 同一组件布局、样式或交互被双方修改。

- 一方删除文件，另一方修改文件。

- 一方重命名文件，另一方修改旧路径。

- 依赖版本或构建配置冲突。

- 数据模型或迁移脚本顺序冲突。

常见功能冲突类型：

- 两个分支都修改了同一功能的业务规则，但规则不一致。

- 一个分支修改了接口请求或响应结构，另一个分支仍按旧结构使用。

- 一个分支新增权限校验，另一个分支新增入口但没有适配权限。

- 一个分支修改数据模型，另一个分支修改依赖旧模型的展示或计算逻辑。

- 一个分支修改会话、消息、Agent 等核心状态流，另一个分支修改同一状态的消费逻辑。

- 一个分支修改 Web 行为，另一个分支修改桌面端或 Android 行为，导致多端表现不一致。

- 一个分支修改 UI 交互路径，另一个分支新增功能入口，导致入口、状态或反馈逻辑冲突。

- 一个分支修改错误处理或回退逻辑，另一个分支引入新异常路径但没有接入。

冲突汇报格式：

```Markdown
冲突位置：
1. 文件：...
   功能：...
   当前分支改动：...
   目标分支改动：...
   冲突原因：...
   冲突类型：代码冲突 / 功能冲突 / 两者都有
   风险：...
```

## 功能冲突分析

功能冲突是指代码可以合并、构建也可能通过，但合并后的业务行为不正确、不一致或不符合任一分支原本意图。

分析功能冲突时，必须检查：

- 用户故事是否发生冲突。

- 验收条件是否互相矛盾。

- API 请求、响应、错误码、字段含义是否一致。

- 数据模型、默认值、迁移逻辑是否兼容。

- 权限、认证、角色判断是否一致。

- 前端状态流、缓存、刷新后状态是否一致。

- Web、桌面端、Android 是否需要保持同一行为。

- 是否有一个分支新增能力，而另一个分支修改了该能力依赖的基础逻辑。

功能冲突汇报格式：

```Markdown
功能冲突：
1. 功能：...
   当前分支行为：...
   目标分支行为：...
   冲突原因：...
   推荐统一后的行为：...
   需要修改的模块：...
   验证方式：...
```

## 合并方案要求

执行合并前，AI 或协作者必须给出方案。

方案必须包含：

- 当前分支和目标分支。

- 当前工作区状态。

- 目标分支改动摘要。

- 修改范围。

- 预计或实际冲突位置。

- 每个代码冲突和功能冲突的原因。

- 推荐合并方式。

- 每个冲突的处理方案。

- 验证和回归测试计划。

- 是否需要用户确认。

如果已经发生冲突，不能只说“有冲突”。必须逐项给出：

- 冲突文件。

- 功能冲突点。

- 保留当前分支哪些逻辑。

- 保留目标分支哪些逻辑。

- 需要人工重写或整合的部分。

- 修改后的预期行为。

## 推荐合并方式

根据情况选择：

- `git merge 目标分支`：适合保留分支历史，常用于功能分支合入主分支。

- `git rebase 目标分支`：适合让当前分支基于目标分支最新提交继续开发，但会改写当前分支提交历史。

- `git cherry-pick 提交`：适合只引入目标分支中的部分提交。

- 手动移植：适合目标分支过大、冲突复杂、只需要部分逻辑的情况。

选择标准：

- 如果用户只是要把某个功能分支合进当前分支，默认优先 `merge`。

- 如果需要保持线性历史，且用户明确允许改写当前分支历史，可以考虑 `rebase`。

- 如果只需要少数提交，优先 `cherry-pick`。

- 如果目标分支包含大量无关改动，优先拆分或手动移植。

## 冲突处理规则

发生冲突时：

- 先列出冲突文件。

- 逐个文件分析冲突原因。

- 逐个功能分析是否存在语义冲突。

- 保留双方必要逻辑，而不是机械选择一边。

- 对公共组件、数据结构、接口契约、构建配置冲突要特别谨慎。

- 对每个冲突给出明确修改方案，再开始改代码。

- 如果冲突会改变用户可见行为，必须说明新行为。

- 解决冲突后重新检查 diff。

- 不把冲突标记提交进仓库。

建议命令：

```Bash
git status
git diff
git diff --check
```

## 冲突解决方案模板

```Markdown
冲突解决方案：

1. 文件：...
   冲突位置：...
   冲突类型：代码冲突 / 功能冲突 / 两者都有
   处理方式：...
   保留当前分支：...
   保留目标分支：...
   需要重写：...
   修改后行为：...
   验证方式：...

2. 文件：...
   ...
```

如果存在多种可行方案，必须说明推荐方案和不推荐其他方案的原因。

## 合并后验证

合并完成后，至少执行：

- 直接受影响功能的验收测试。

- 可能受影响功能的回归测试。

- 构建检查。

- lint 或类型检查，如果项目支持。

- 关键接口或页面的手动验证。

验证范围应根据目标分支改动决定：

- 后端改动：运行相关单元测试、接口测试、服务启动检查。

- Web 改动：运行构建，检查受影响页面和交互。

- 桌面端改动：运行桌面端构建或启动检查。

- Android 改动：运行同步、构建或真机/模拟器验证。

- 数据结构改动：检查旧数据兼容性和迁移风险。

## 禁止事项

- 禁止在工作区不干净时直接合并。

- 禁止未经确认执行会丢失改动的命令。

- 禁止不分析目标分支就直接合并。

- 禁止只解决编译错误而不检查业务行为。

- 禁止把未验证的合并结果描述为已完成。

- 禁止为了快速合并而覆盖用户已有改动。

## 默认流程

1. 检查当前 git 状态。

2. 如果工作区不干净，建议用户先提交或处理当前改动。

3. 拉取远端分支信息。

4. 分析目标分支引入的提交和文件改动。

5. 归类影响范围。

6. 给出合并方案和测试计划。

7. 等用户确认。

8. 执行合并。

9. 解决冲突。

10. 运行验证和回归测试。

11. 汇报结果，并建议用户提交合并后的稳定状态。
