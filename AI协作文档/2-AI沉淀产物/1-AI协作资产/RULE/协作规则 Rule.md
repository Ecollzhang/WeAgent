# 协作规则 Rule

本文档定义我们在具体执行需求时遵守的协作规则。

# 默认协作循环

- 用户提出需求。

    - AI 复述需求，明确理解和假设。

    - AI 阅读相关代码，不凭空设计。

    - AI 给出分阶段方案。

    - AI 在方案中列出需要确认的问题。

- 用户一次性答复、协商或修改方案。

    - AI 执行当前阶段。

    - AI 编写或运行测试。

    - AI 汇报阶段成果和验证结果。

- 用户检查。

    - AI 根据反馈修正，或进入下一阶段。

# 沟通规则

- 先说明正在做什么，再执行较大改动。

- 发现需求歧义时，先写出合理假设。

- 问题集中提问，不零散打断。

- 用户反馈优先级高于原计划。

- 不用笼统承诺代替可验证结果。

- 不把“已实现”说成“已验证”。

# 需求理解规则

AI 在实现前必须确认：

- 目标用户是谁。

- 操作入口在哪里。

- 期望行为是什么。

- 当前行为哪里不对。

- 哪些端需要同步：Web、桌面端、Android、后端。

- 是否需要数据持久化。

- 是否需要兼容历史数据。

- 是否涉及构建、打包、部署。

# 方案规则

方案必须满足：

- 分阶段。

- 每阶段目标明确。

- 每阶段可独立验证。

- 每阶段范围尽量小。

- 明确哪些文件或模块会被影响。

- 明确验收标准。

- 明确测试方式。

- 明确风险和依赖。

# 实现规则

- 先读代码，再改代码。

- 遵循项目现有架构和风格。

- 不做无关重构。

- 不覆盖用户已有改动。

- 每次只改当前阶段需要的内容。

- 修改共享逻辑时同步考虑 Web、桌面端、Android、后端的影响。

- 对实时事件、数据持久化、刷新后状态要同时验证。

- 对 UI 改动要考虑实时状态、刷新状态、空状态、错误状态。

# 测试规则

每阶段必须有测试或验证。

优先顺序：

- 能写自动化测试就写自动化测试。

- 不能写自动化测试就写最小验证脚本。

- 前端和桌面端改动至少跑构建。

- 后端 Python 改动至少跑语法检查或相关单测。

- UI 行为必须提供手动验证步骤。

测试报告必须写清：

- 跑了什么命令。

- 结果是什么。

- 有哪些 warning。

- 哪些测试没跑，为什么。

# 阶段验收规则

每个阶段结束时必须汇报：

- 完成了什么。

- 改了哪些主要文件。

- 如何验证。

- 是否有遗留风险。

- 下一阶段是什么。

用户检查后：

- 如果用户要求修正，先修当前阶段。

- 如果用户确认继续，再进入下一阶段。

- 如果用户改变需求，更新方案。

# 迭代精炼规则

- 小步快跑。

- 一次只解决一个主要问题。

- 优先修复可复现问题。

- 每次修复都要说明原因。

- 同类问题要找根因，不只修表象。

- 修复后要验证实时状态和刷新后状态是否一致。

- 如果多端共享逻辑不同步，要明确说明并安排同步阶段。

# 冲突处理规则

当出现冲突时，优先级如下：

- 用户最新明确指令。

- 数据安全和不破坏已有工作。

- 当前阶段验收标准。

- 项目既有架构和约定。

- 原计划。

- 如果无法同时满足，AI 必须说明冲突点，并给出推荐取舍。

# 完成汇报规则

最终回复保持简洁，但必须包含：

- 关键改动。

- 验证结果。

- 需要用户做的动作，例如重启后端、刷新前端、重新打包。

- 未完成或未验证的内容。

- 不使用空泛表述，不隐藏失败，不把 warning 说成错误
