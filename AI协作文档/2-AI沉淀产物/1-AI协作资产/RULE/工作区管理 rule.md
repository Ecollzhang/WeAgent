# 工作区管理 rule

> 本文档定义了 AI 协作过程中必须遵守的操作约束。
> 所有规则按优先级排列，冲突时以安全为最高原则。
> 
> 

---

## 1\. 文件操作安全

### 1\.1 删除操作

- 删除任何文件或目录前，必须先向用户确认

- 确认内容需包含：目标路径、文件大小、是否可恢复

- 禁止使用 `rm -rf` 等不可逆命令，除非用户明确授权

- 优先使用回收站或 `git stash` 等可恢复方式

- 批量删除（超过 5 个文件）需额外说明删除原因并逐一列出

- 删除前检查文件是否被其他模块引用或导入

### 1\.2 覆盖操作

- 覆盖已有文件前，需提示用户原文件存在

- 对配置文件（`.env`, `settings.json`, `docker-compose.yml`, `nginx.conf` 等）的修改，需先展示 diff 再执行

- 对超过 50 行的已有文件进行全量重写前，需向用户确认

- 覆盖时保留原文件的权限位和特殊属性

- 如果原文件有本地修改（相对于 git），需特别提醒

### 1\.3 移动/重命名

- 移动或重命名文件前，需告知用户原路径和目标路径

- 涉及导入路径变更的重命名，需列出所有受影响的文件

- 重命名后检查是否有硬链接、软链接指向原路径

- 批量重命名需先展示完整的映射表

### 1\.4 符号链接

- 创建符号链接前，确认目标路径存在

- 不创建指向临时目录或可变路径的符号链接

- 删除符号链接时说明它指向的目标

### 1\.5 文件编码

- 新建文件统一使用 UTF\-8 编码

- 修改已有文件时保持原编码不变

- 涉及编码转换的操作需向用户确认

### 1\.6 大文件

- 单个文件超过 1MB 时，操作前需提醒用户

- 不将二进制文件（图片、视频、编译产物等）纳入常规代码修改流程

- 超过 100MB 的文件需建议使用 Git LFS 或其他大文件方案

## 2\. 疑问处理

### 2\.1 必须询问的场景

- 用户指令存在多种合理解读时

- 涉及架构或设计方向的选择时

- 操作结果不可逆或影响范围较大时

- 用户需求不完整，缺少关键信息时

- 存在已知的替代方案且各有优劣时

- 修改会影响已有功能的行为时

- 涉及安全相关的配置（认证、权限、加密）时

- 需要选择第三方库或工具时

### 2\.2 可以自行判断的场景

- 明确的单义性指令

- 常规代码格式调整（缩进、空格、import 排序）

- 已有约定的重复性操作

- 文档中的明显笔误修正

- 纯粹的变量重命名（不影响逻辑）

- 日志信息的微调

### 2\.3 询问方式

- 提供选项而非开放式问题（2\-4 个选项）

- 每个选项附带简短说明和影响

- 如有推荐选项，标注 `(推荐)` 并说明理由

- 紧急问题优先使用简短确认，非紧急问题可以详细展开

- 复杂决策附带简单的对比表格

### 2\.4 需求澄清模板

当需求不明确时，使用以下结构提问：

```Plain Text
🔍 需求澄清

您的指令：[用户原文]

我理解的意图：[我的解读]

需要确认：
[具体问题 A]？
[具体问题 B]？

可选方案：
方案 A：[描述]（优点 / 缺点）
方案 B：[描述]（优点 / 缺点）
```

## 3\. Git 操作规范

### 3\.1 分支管理

- 修改代码前，确认当前分支是否正确

- 不在 `main` 分支直接提交代码

- 创建新分支使用语义化前缀，格式：`<type>/<description>`

- type 取值：

|**type**|**用途**|**示例**|
|---|---|---|
|feat|新功能|feat/user\-login|
|bugfix|修复 bug|bugfix/null\-pointer|
|refactor|重构（不改变功能）|refactor/auth\-module|
|docs|文档变更|docs/api\-guide|
|style|代码格式调整|style/lint\-fix|
|test|测试相关|test/auth\-unit|
|chore|构建、工具、配置等|chore/deps\-update|
|perf|性能优化|perf/query\-cache|
|ci|CI/CD 相关|ci/add\-lint\-step|

- description 使用英文短横线分隔

- 分支名全部小写，单词间用短横线连接

- 不使用特殊字符或中文作为分支名

### 3\.2 提交规范

- 提交信息使用 Conventional Commits 格式

- 格式：`<type>(<scope>): <description>`

- description 使用中文

- 示例：

    - `feat(auth): 添加用户登录功能`

    - `fix(api): 修复空指针异常`

    - `refactor(utils): 拆分工具函数模块`

    - `docs(readme): 更新部署说明`

    - `perf(db): 添加查询结果缓存`

    - `chore(deps): 升级 axios 到 1.6.0`

- 每次提交只包含逻辑上相关的变更，不做大杂烩提交

- 提交信息不超过 72 个字符

- 需要详细说明时，空一行后添加 body：

- feat\(auth\): 添加 OAuth2 登录支持

\- 集成 Google OAuth2 provider
\- 添加 token 刷新机制
\- 更新用户表增加 oauth\_id 字段

Closes \#123

### 3\.3 变更预览

- 执行 `git add` 前，展示待暂存的文件列表

- 执行 `git commit` 前，展示变更摘要（文件数、增删行数）

- 不自动执行 `git push`，除非用户明确要求

- 大型变更（超过 20 个文件或 500 行）需分批提交并说明分批逻辑

### 3\.4 危险操作

以下操作执行前必须向用户确认：

|**操作**|**风险说明**|**替代方案**|
|---|---|---|
|git push \-\-force|可能覆盖远程提交历史|git push \-\-force\-with\-lease|
|git reset \-\-hard|丢失未提交的本地修改|git stash 先暂存|
|git branch \-D|强制删除未合并分支|先 git merge 或 git cherry\-pick|
|git checkout \-\- \<file\>|丢弃工作区修改|先 git stash 保留副本|
|git clean \-fd|删除未跟踪文件|先 git clean \-fdn（dry\-run）|
|git rebase \-i|交互式变基可能丢失提交|确保在新分支上操作|

### 3\.5 合并策略

- 优先使用 `git merge --no-ff` 保留分支历史

- 长期分支同步使用 `git rebase` 保持线性历史

- 合并冲突时，先展示冲突文件列表，再逐一解决

- 解决冲突后需确认所有冲突标记已清除（`<<<<<<<`, `=======`, `>>>>>>>`）

- 不自动选择冲突的某一侧，需向用户说明两侧差异

### 3\.6 标签管理

- 发布版本使用语义化标签：`v<major>.<minor>.<patch>`

- 标签附带注释说明版本内容

- 不删除已推送到远程的标签

## 4\. 外部操作

### 4\.1 网络请求

- 调用外部 API 或发送网络请求前，告知用户目标地址和用途

- 不将敏感数据（token、密码、密钥）发送到外部服务

- 网络请求设置合理的超时时间

- 处理网络异常和重试逻辑

### 4\.2 依赖管理

- 安装新依赖前，需确认：

    - 包名和版本

    - 是否有已知安全漏洞

    - 是否与现有依赖冲突

    - 是否有更轻量的替代方案

- 不随意升级已有依赖的主版本

- 升级依赖后需运行测试确认兼容性

- 移除依赖前检查是否有其他模块在使用

### 4\.3 环境变更

- 修改环境变量前需确认

- 修改系统配置（hosts, proxy, PATH 等）前需确认

- 启动或停止服务前需确认

- 修改数据库结构（schema migration）前需确认并提供回滚方案

- 端口占用、进程状态等运行时信息需提前检查

### 4\.4 容器与服务

- Docker 相关操作前确认镜像名称和版本

- 不使用 `latest` 标签，锁定具体版本

- 容器数据卷挂载前确认宿主机路径

- 修改 docker\-compose 需先展示 diff

## 5\. 测试规则

### 5\.1 测试执行

- 代码修改后，建议运行相关测试

- 运行测试前说明测试范围和预期耗时

- 测试失败时，先分析失败原因，不盲目重跑

- 不修改测试用例来让测试通过（除非测试本身有误）

### 5\.2 测试编写

- 新增功能需配套单元测试

- 修复 bug 需补充回归测试

- 测试命名清晰，体现被测行为

- 测试数据与生产数据隔离

- 测试可重复执行，不依赖外部状态

### 5\.3 测试覆盖率

- 不追求 100% 覆盖率，但关键路径必须覆盖

- 关注边界条件和异常路径的测试

- 新增代码的测试覆盖率不低于项目平均水平

---

## 6\. 文档规则

### 6\.1 代码文档

- 公开函数和类必须有 docstring

- 复杂算法需附带思路说明

- 不写显而易见的注释（如 `i += 1  # 递增 i`）

- 注释解释"为什么"，而非"做了什么"

- API 变更需同步更新接口文档

### 6\.2 项目文档

- README 保持最新，包含：项目简介、安装步骤、使用说明

- 重大架构变更需更新架构文档

- 配置变更需更新配置说明

- 文档中的代码示例需可运行

### 6\.3 变更日志

- 用户可见的功能变更需记录 CHANGELOG

- 格式遵循 Keep a Changelog 规范

- 分类：Added / Changed / Deprecated / Removed / Fixed / Security

## 7\. 信息展示

### 7\.1 操作汇报格式

完成重要操作后，使用以下格式汇报：

```Plain Text
📋 操作摘要
[主要操作]
[修改的文件]

📊 当前状态
[Git/文件系统/运行时状态]

💡 后续建议
[下一步操作建议]
```



### 7\.2 变更对比展示

展示代码变更时使用统一格式：

- 旧代码（删除的部分）

- 新代码（新增的部分）

上下文行（未变更）

### 7\.3 错误处理

- 遇到错误时，先分析原因再尝试修复

- 同一错误不重试超过 2 次

- 重试前需告知用户错误原因和重试方案

- 无法自行解决时，明确告知用户问题所在和建议的解决方向

- 错误信息需包含：

    - 错误类型和消息

    - 发生位置（文件:行号）

    - 可能的原因

    - 建议的修复方向

## 8\. 安全约束

### 8\.1 密钥与凭证

- 不在代码中硬编码任何密钥、密码、token

- 不将 `.env` 文件提交到 git

- 不在日志中输出敏感信息

- 不在错误消息中暴露内部路径或配置细节

### 8\.2 输入验证

- 所有外部输入需验证和清理

- SQL 查询使用参数化查询，不拼接字符串

- 文件路径操作需防止路径穿越

- 用户上传的文件需检查类型和大小

### 8\.3 权限控制

- 文件权限遵循最小权限原则

- 不随意使用 `chmod 777`

- 数据库连接使用最小权限账号

- API 接口需有适当的认证和授权

---

## 9\. 性能意识

### 9\.1 代码层面

- 避免在循环中执行 I/O 操作

- 大数据集使用流式处理，不一次性加载到内存

- N\+1 查询问题需使用批量查询或 eager loading

- 热点路径避免不必要的对象创建

### 9\.2 数据库层面

- 查询需有索引支持

- 不在生产环境执行全表扫描

- 大批量操作使用分批处理

- 迁移脚本需评估执行时间和锁表影响

---

## 10\. 紧急情况处理

### 10\.1 生产事故

- 发现生产问题立即告知用户

- 优先止血（回滚、降级、熔断），再定位根因

- 保留现场信息（日志、截图、错误码）

- 修复后补充事故报告

### 10\.2 数据安全

- 涉及数据删除的操作，必须有备份方案

- 批量数据修改前，先在小范围验证

- 数据库迁移脚本必须可回滚

---

## 附录 A：规则优先级

当规则之间存在冲突时，按以下优先级处理：

安全约束 \> 文件安全 \> Git 规范 \> 测试完整性 \> 文档完善 \> 性能优化
