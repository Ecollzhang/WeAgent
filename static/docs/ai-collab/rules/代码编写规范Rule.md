# 代码编写规范 Rule

本文档是用户与 AI 编程助手协作时必须遵守的代码编写规范。后续由 AI 编写、修改、重构或生成代码时，应优先遵守本文档；若与具体需求、现有架构或安全约束冲突，应先说明冲突点，再给出处理方案。

## 1. 基本原则

- 保持工作区边界清晰。开始新需求前，应提醒用户尽量先提交已完成且稳定的功能，保持 Git 工作区和暂存区干净。
- 不随意重构无关代码。只修改当前需求直接相关的文件和模块。
- 先理解现有实现，再编写代码。优先阅读现有目录结构、接口、组件、服务和测试，不凭空引入新架构。
- 优先复用项目已有模式。命名、目录、状态管理、API 调用、错误处理、样式组织应尽量与现有代码保持一致。
- 代码应可维护、可测试、可回滚。每个改动都应有明确目的，避免把多个无关需求混在一次修改中。
- 完成阶段性需求后，必须做可能受影响功能的回归验证；无法自动测试时，应给出明确的人工验证清单。

## 2. 前端开发规范

- 使用组件化开发。复杂页面应拆分为清晰的视图组件、业务组件、展示组件和通用组件。
- 单个组件只承担明确职责。避免一个组件同时处理页面布局、接口请求、复杂业务逻辑、弹窗、编辑器和状态同步。
- API 调用应集中在 API service 层，不在组件中散落拼接后端地址或重复封装请求逻辑。
- 状态命名要清晰。区分 loading、saving、submitting、streaming、error、empty 等状态，避免复用同一个布尔值表达多种含义。
- 表单应有明确的校验、提交中状态、错误提示和成功反馈。
- 列表、弹窗、抽屉、工作台等交互应处理空状态、加载状态、失败状态和刷新状态。
- 消息、产物、工作流、文件等核心展示应支持刷新恢复，不依赖只存在内存中的临时状态。
- Markdown、代码块、表格、图片、HTML、diff、workflow、service 等多类型内容应按类型渲染，不把结构化产物退化成纯文本。
- UI 样式应保持端内一致。Web、Desktop、Android 可以有端侧差异，但同一端内按钮、卡片、字号、间距、滚动条和弹窗风格应统一。
- 组件内样式应避免污染全局。只有通用基础样式、主题变量或全局滚动条等才应放入全局样式文件。

## 3. 后端开发规范

- 后端代码应保持模块化。Controller 负责请求解析和响应，Service 负责业务逻辑，Model 负责数据结构，Repository 或查询逻辑应保持集中。
- 接口定义要稳定清晰。请求字段、响应结构、错误格式、状态码和权限边界应明确，不随意改变已有契约。
- 业务逻辑不应堆在 Controller 中。复杂逻辑必须下沉到 service 或专门模块。
- 数据模型字段要有明确含义。新增字段前应确认是否已有字段可复用，避免重复表达同一状态。
- 后端错误应可定位。异常信息应进入日志、消息状态、AgentRun 或前端可见错误，不只在控制台打印。
- 不把临时调试逻辑写入正式链路。调试日志、mock 数据和临时兼容逻辑应在完成后清理或明确隔离。
- 长任务必须异步化或事件化。Agent 执行、沙箱事件、Provider 输出和产物生成不应依赖单个 HTTP 请求阻塞等待。
- 后端需要兼顾 Web、Desktop、Android 三端，不应为某一端写破坏统一协议的特殊接口，除非明确说明端侧原因。

## 4. API 与数据契约规范

- API 路由应符合现有分组：auth、conversations、messages、agents、artifacts、sandbox、capabilities、settings、upload 等。
- 请求 schema 与前端 payload 必须同步。新增字段时，应同时检查 schema、service、前端 API 和调用点。
- 响应数据应尽量稳定。新增字段可以兼容，删除或改名字段必须评估 Web、Desktop、Android 影响。
- 对于会话、消息、AgentRun、Message.elements、raw_output、Artifact、sandbox session 等核心模型，应明确字段归属。
- `Artifact` 表不是所有产物的统一存储。运行时产物可能存在于 `Message.elements`、`Message.raw_output`、容器文件系统或服务状态中。
- 会话级 Agent 配置只影响当前会话执行，不应回写全局 Agent。
- 实时事件应能通过持久化数据恢复。Socket.IO 推送是增量通道，刷新后必须能通过 REST API 恢复主要状态。

## 5. 后端安全与权限规范

- 用户只能访问自己有权限的会话、消息、文件、服务和能力配置。
- 上传文件必须校验文件名、后缀、大小和保存路径，不允许路径穿越。
- 不把 API Key、认证文件、Provider secret 或 token 返回给前端。
- 不把超长 base64 图片写入短字符串字段。头像、图片和附件应优先保存为文件，再存 URL。
- 错误响应不能泄漏敏感配置、数据库连接串、密钥或容器内部敏感路径。
- 删除、停止、迁移、写文件等操作必须明确目标资源和权限边界。

## 6. Docker 与 Sandbox 开发规范

- Agent 执行必须限制在 Docker Sandbox 或明确的受控运行环境内，不应直接在宿主机项目目录执行不可信任务。
- 容器文件访问必须通过后端 Sandbox API 代理，前端不能直接访问容器文件系统。
- 容器服务预览必须通过 Service Proxy 暴露，不直接暴露容器端口。
- Dockerfile 和容器启动脚本应最小化权限，不安装无关工具，不默认开放无关端口。
- Provider CLI、MCP Runtime、工具调用和服务进程应有清晰的日志、错误和停止机制。
- 文件读写应限制在工作区允许范围内，防止路径穿越和覆盖系统文件。
- 容器 API 与宿主后端代理路径必须保持一致，避免出现宿主访问容器 404。
- 镜像构建、容器启动和 Provider CLI 安装变更后，应验证 `weagent-sandbox:latest` 是否可用。

## 7. Provider Adapter 与能力系统规范

- Agent Adapter 用于选择底层 AI Coding 执行引擎，例如 Claude Code、Codex、OpenCode。
- ToolProviderConfig 用于配置能力或工具的外部 Provider，不等同于 Agent Adapter。
- 新增 Provider 时，应优先新增 Provider Runner，不应把 Provider 特殊逻辑写散到消息服务或前端组件中。
- Provider Runner 应统一处理命令构造、环境变量、认证、stdout、stderr、超时、停止和错误状态。
- Skill、Tool、MCP、Plugin 应通过 Capability 系统管理，经过导入、审查、绑定、投影后进入容器。
- 能力投影应是会话级、Agent 可见的运行视图，不应让 Agent 直接读取全局能力库。

## 8. 前后端实时通信规范

- REST API 负责提交请求和读取状态，Socket.IO 负责实时推送执行过程。
- 客户端进入会话详情后，应加入对应 conversation room。
- 消息创建、状态变化、元素增量和工作流计划应使用统一事件语义。
- 前端处理实时事件时，应按 message id、element id 或 run id 合并更新，避免重复插入。
- Socket.IO 断开、重连或页面刷新后，应通过消息列表接口恢复 `Message.elements` 和 `Message.raw_output`。

## 9. 测试与回归规范

- 每个阶段性需求完成后，应执行相关功能的回归测试。
- 后端改动应优先运行对应单元测试、接口测试或最小可复现脚本。
- 前端改动应至少验证受影响页面的构建、关键交互、空状态、错误状态和刷新恢复。
- 涉及 Web、Desktop、Android 共用协议时，应检查三端是否受影响。
- 涉及消息、产物、工作流、文件、服务或能力投影时，应验证刷新后状态不丢失。
- 涉及 Docker、Provider CLI、MCP、Service Proxy 时，应验证容器镜像、容器路由、服务日志和错误回写。
- 如果无法运行自动化测试，应明确说明原因，并给出人工验证步骤。

## 10. Git 与交付规范

- 开始新需求前，应建议用户先提交已完成且稳定的功能，保持工作区干净。
- 修改前应查看当前 Git 状态，识别未提交文件，避免覆盖用户已有改动。
- 不允许擅自执行 `git reset --hard`、`git checkout --` 等破坏性操作。
- 不把无关格式化、无关重构和需求实现混在一次提交中。
- 阶段性完成后，应说明修改了哪些文件、验证了什么、哪些测试未运行及原因。
- 如果修改跨多个模块，应建议按阶段或按功能提交，便于回滚和审查。

## 11. 文档与注释规范

- 复杂设计应同步更新相关 README、技术文档、使用手册或方案文档。
- 注释用于解释复杂意图、边界和非显然逻辑，不用于重复代码字面含义。
- 文档中的接口、字段、路径和命令应与真实代码保持一致。
- 架构图、时序图和说明文字应标明边界，不把未验证能力写成已完成事实。
- 文档修改也应经过格式检查，至少执行 Markdown 基础审查或 `git diff --check`。

## 12. AI 编码助手执行要求

- AI 在实现需求前，应先理解需求和现有代码，再决定修改方案。
- 对复杂需求，应先拆阶段、列验收标准和测试方式，再逐步实现。
- AI 不应为追求一次完成而扩大需求范围。
- AI 每次完成代码改动后，应报告修改内容、验证结果、未验证项和风险。
- AI 发现需求与现有架构冲突时，应先说明冲突，再给出可执行方案。
- AI 发现当前工作区存在大量未提交改动时，应提醒用户先提交稳定功能，再继续后续需求。
