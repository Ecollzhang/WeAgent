# WeAgent排障 Skill

> 版本：v2\-draft
> 
> 来源重构：`S05-Debug排查Skill.md`
> 
> 目标：把通用 debug 流程改造成可复用、但带有 WeAgent 真实链路锚点的排障 skill。
> 
> 

---

## 1\. 适用场景

适用于以下问题：

- 前端已经出现异常现象，但不确定断在哪一层

- 消息发出了，但 Agent 没回、回了但界面没显示、显示了但产物不对

- 容器文件、产物预览、卡片渲染、事件流存在链路中断

不适用于以下情况：

- 需求还没定义清楚，问题本质仍是方案问题

- 主链从未跑通过，当前不是“排障”而是“首次实现”

- 没有最小复现现象，只是模糊怀疑“可能有 bug”

---

## 2\. 核心方法

这份 skill 的通用方法是：

```Plain Text
先按链路分层
→ 再用现象定位优先检查层
→ 再看关键日志 / 关键文件
→ 最后确认真实根因与修复结果
```

它和普通 debug 流程的区别，不是“也会看日志”，而是：

- 按 WeAgent 的真实消息 / 产物链路分层

- 先判断最可能断在哪一层，而不是无差别翻代码

- 验证不只看“当前好了没”，还要看刷新后、重进后、跨端后是否仍成立

---

## 3\. WeAgent 五层排障模型

### L1\. 前端交互层

关注点：

- 点击、发送、查看、预览等操作是否真的触发

- 本地状态、参数拼装、弹窗渲染、卡片展示是否异常

常看材料：

- 页面控制台日志

- 组件事件处理函数

- 请求参数、Socket 发送内容

### L2\. 消息服务层

关注点：

- 请求是否进入后端

- schema / controller / service 是否接受并处理了数据

常看材料：

- 接口请求记录

- `message_service` 相关日志

- 参数校验报错、字段缺失报错

### L3\. 编排与事件层

关注点：

- Orchestrator 是否正确驱动消息流、步骤流、状态流

- Socket 事件是否发出、emit 路径是否完整

常看材料：

- 事件发送代码

- 中间状态日志

- 卡片 / 消息元素的 emit 逻辑

### L4\. Adapter / Agent 层

关注点：

- Adapter 是否把平台输出正确转换为系统内部消息

- Agent 返回的结构是否符合预期

常看材料：

- Adapter 输入输出

- 原始模型返回

- 结构化解析逻辑

### L5\. Sandbox / 文件层

关注点：

- 容器是否创建成功

- 文件是否真的生成、写回、读取、映射成功

常看材料：

- sandbox 日志

- 文件树接口

- 容器读写路径

## 4\. 现象到排查层的优先映射

|现象|优先检查层|关键日志 / 关键文件|常见根因|
|---|---|---|---|
|点击后没有任何响应|L1 前端交互层|控制台、点击事件函数|事件未绑定、参数未传、状态未更新|
|请求发出但后端报字段错误|L2 消息服务层|schema / controller / service|请求结构变了、字段名不兼容|
|Agent 有结果但界面没显示|L3 编排与事件层|emit 逻辑、消息元素流|事件没发出、只覆盖一种出口、流中断|
|模型返回正常但结构化消息错乱|L4 Adapter / Agent 层|adapter 输入输出、解析逻辑|结构转换不一致、字段映射错误|
|产物预览失败 / 文件读不到|L5 Sandbox / 文件层|文件树接口、路径、容器日志|文件未落盘、路径硬编码、容器接口不一致|

---

## 5\. 标准排障步骤

### 第一步：固定异常现象

至少写清楚：

- 用户做了什么动作

- 当前看到什么异常

- 正常情况下本该出现什么结果

- 能否稳定复现

### 第二步：先判层，再查代码

不要上来全局搜索。

先根据“现象到排查层映射表”判断最可能的 1\-2 层，然后只看这些层的关键日志和关键文件。

### 第三步：确认真实根因

根因确认标准：

- 能解释异常为什么发生

- 能解释为什么有些路径正常、有些路径不正常

- 修掉后能同时消除当前现象和对应副作用

如果只能说“改完好像好了”，不算根因确认。

### 第四步：做双重验证

至少做两类验证：

- 当前路径立即验证

- 刷新 / 重进 / 再次触发后的稳定性验证

如果问题涉及文件、容器或状态流，再补：

- 文件是否真实落盘

- 跨端或二次进入时是否仍成立

## 6\. WeAgent 真实案例锚点

### 案例 A：emit 路径断裂

来源：

- `handoff-P3-editor.md`

- 与统一编辑平台、卡片生成相关的收口 / 归档材料

现象：

- 某些消息或卡片在一条链路上能显示，另一条链路上不显示

优先检查层：

- L3 编排与事件层

根因类型：

- emit 逻辑只覆盖了一种出口，另一条消息路径没有同步注册

提炼出的通用判断：

- 遇到“部分显示、部分不显示”时，优先怀疑事件出口不完整，而不是先怀疑前端渲染

### 案例 B：容器文件读写失败

来源：

- 与 sandbox 文件树、容器文件读取相关的 session / spec / debug 材料

现象：

- 页面尝试查看产物，但文件不存在、接口 404、或路径读取失败

优先检查层：

- L5 Sandbox / 文件层

根因类型：

- 文件没有真正写回容器

- 路径硬编码

- 容器接口版本不一致

提炼出的通用判断：

- 遇到“前端入口正常、预览失败、接口报文件问题”时，先确认文件是否真实存在，再看前端

---

## 7\. 输出格式

建议一次排障至少输出：

- 异常现象

- 优先怀疑层

- 检查过的日志 / 文件

- 确认的真实根因

- 修复动作

- 验证结论

- 是否需要进入收口阶段

---

## 8\. 失败边界

以下情况说明当前工作不应继续按排障推进：

- 三轮检查后仍无法定位到具体层级

- 所谓“异常”本质是需求未定义或方案冲突

- 主链从未跑通，当前只能回退到实现或方案阶段

此时应停止把问题包装成 debug，转为：

- 方案重审

- 主链补齐

- 范围重定义
