# WeAgent 对话沙箱化与多 Agent 协作实现方案

## 1. 目标需求复述

目标是在正式对话列表中同时支持两类会话：

- 单 Agent 会话：用户与单个 Agent 沟通，由该 Agent 独立完成任务。
- 多 Agent 协作会话：用户与多个 Agent 沟通，其中包含一个主持 Agent，负责理解任务、拆分任务、分发给其他 Agent，并组织协作。

每个对话都应创建一个 Docker 容器。容器内需要有：

- 每个 Agent 独立工作目录，例如 `/workspace/agents/{agent_id}/`。
- 多 Agent 共享工作目录，例如 `/workspace/shared/`。
- 可访问和预览 Agent 工作目录、共享目录中的文件。
- 可独立停止每个 Agent 当前任务。
- 每个 Agent 一轮回复对应前端一个消息框。
- 每个消息框支持 Claude Code 全量流式输出，以及文本、图片、代码、表格、文件等结构化内容展示。

## 1.1 已确认产品决策

- Docker workspace 不需要持久化。容器销毁后 `/workspace` 可以丢失，后续如需保留产物再考虑写入数据库。
- 多 Agent 会话创建时，只要用户选择两个或两个以上普通 Agent，系统必须自动加入一个内置主持 Agent。主持 Agent 需要作为预设 Agent 写入数据库，并在 Agent 列表中可见。
- 多 Agent worker 的执行顺序由主持 Agent 安排。主持 Agent 可以决定哪些任务并行、哪些任务串行，后端需要支持结构化执行计划。
- Claude Code 原始输出以折叠方式展示。消息正文优先展示结构化 summary/elements。
- 删除对话时销毁对应 Docker 容器。对话 1 天没有活动时自动停止容器。
- 模型/API Key 配置来源为用户在 Settings 页面保存的配置。
- 正式聊天实时协议统一使用 SocketIO。SSE 可以删除或仅作为过渡兼容，不作为新功能主链路。


## 4. 推荐实现方案

### 4.1 总体设计

将“正式对话”与“沙箱 session”合并为同一业务对象：

```text
Conversation
  1:1 SandboxSession
  1:N ConversationParticipant
  1:N Message
  1:N AgentRun
```

核心链路：

```text
用户创建对话
  -> 后端创建 Conversation
  -> 后端创建 Docker 沙箱 session
  -> 后端在容器内创建对应 Agent
  -> 保存 sandbox_session_id/container 信息

用户发送消息
  -> 保存 user Message
  -> 根据会话类型选择 direct 或 delegate
  -> 为每个参与 Agent 创建 agent Message/AgentRun
  -> 容器内 Claude Code 流式输出
  -> 宿主接收 sandbox_event
  -> 更新对应 Message.elements/content/status
  -> SocketIO 推送前端
  -> 前端增量渲染消息框
```

### 4.2 数据库改造

建议新增或扩展字段。

#### conversations 表新增字段

```text
sandbox_session_id VARCHAR(100)
sandbox_container_id VARCHAR(128)
sandbox_host_port INT
sandbox_status ENUM('pending', 'running', 'stopped', 'error')
moderator_agent_id VARCHAR(36) NULL
last_active_at DATETIME
stopped_at DATETIME NULL
```

#### messages 表新增字段

```text
run_id VARCHAR(36) NULL
status ENUM('pending', 'streaming', 'done', 'error', 'stopped')
round_id VARCHAR(36) NULL
raw_output LONGTEXT NULL
metadata JSON NULL
```

说明：

- `round_id` 表示用户一次发送触发的一轮协作。
- `run_id` 表示某个 Agent 在本轮中的执行实例。
- `raw_output` 存 Claude Code 原始输出，`content/elements` 存展示层内容。

#### 新增 agent_runs 表

```text
id VARCHAR(36) PK
conversation_id VARCHAR(36)
round_id VARCHAR(36)
message_id VARCHAR(36)
agent_id VARCHAR(36)
sandbox_session_id VARCHAR(100)
status ENUM('pending', 'running', 'done', 'error', 'stopped')
started_at DATETIME
finished_at DATETIME
error TEXT
last_seq INT
metadata JSON
```

用途：

- 跟踪每个 Agent 的一轮执行。
- 支持单独停止。
- 支持事件断线恢复。

#### 新增 user_model_configs 表

```text
id VARCHAR(36) PK
user_id VARCHAR(36) UNIQUE
api_key TEXT
base_url VARCHAR(500)
model VARCHAR(100)
temperature FLOAT
max_tokens INT
created_at DATETIME
updated_at DATETIME
```

用途：

- 保存 Settings 页面模型配置。
- 创建 Docker 容器时转换为容器环境变量：
  - `ANTHROPIC_API_KEY`
  - `ANTHROPIC_BASE_URL`
  - `ANTHROPIC_MODEL`
  - 可选 `API_TIMEOUT_MS`
- `api_key` 建议加密存储；如果第一阶段不做加密，也必须在响应中脱敏。

### 4.3 后端服务改造

#### ConversationService

创建会话时：

1. 保存 Conversation 和 participants。
2. 若参与 Agent 数量为 1，创建单 Agent sandbox session。
3. 若参与 Agent 数量大于等于 2，自动加入内置主持 Agent，再创建多 Agent sandbox session。
4. 读取当前用户 Settings 模型配置，转换成 `env_vars`。
5. 调用 `DockerContainerManager.create_session(conversation.id, agents_config, env_vars)`。
5. 保存 sandbox session/container 信息。

需要新增方法：

```python
create_conversation_sandbox(conversation, participants)
recover_conversation_sandbox(conversation_id)
destroy_conversation_sandbox(conversation_id)
stop_inactive_sandboxes()
```

主持 Agent seed 要求：

- 在 `SYSTEM_AGENTS` 中增加固定 ID：`moderator`。
- 主持 Agent 作为系统内置 Agent，在 Agent 列表中可见，但不允许用户编辑；前端只允许查看。
- `adapter_name` 默认 `claude`.
- `system_prompt` 明确要求输出结构化执行计划，并负责按依赖关系调度 worker。
- 多 Agent 创建会话时不允许重复添加主持 Agent。
- 多 Agent 创建会话时，前端不需要也不应该让用户勾选主持 Agent；后端根据普通 Agent 数量自动注入 `moderator`。

#### MessageService

替换当前 `_mock_agent_response()`。

发送用户消息时：

1. 创建用户 Message。
2. 生成 `round_id`。
3. 判断会话参与 Agent。
4. 单 Agent：创建一个 AgentRun 和一个 Agent Message，调用沙箱 direct send。
5. 多 Agent：先创建主持 AgentRun/Message，将用户任务发送给容器内 `moderator` Agent，等待主持 Agent 返回结构化 plan。
6. 后端正式链路解析 plan，并根据 plan 创建 worker AgentRun/Message，按 plan 中的并行组和依赖关系调度；容器只负责执行指定 Agent 的具体任务，不负责正式业务调度。
6. 所有执行事件由沙箱事件回调统一更新。

建议新增服务：

```text
SandboxConversationService
AgentRunService
MessageElementBuilder
```

不要把所有逻辑继续塞进 `message_service.py`。

#### Sandbox event callback

当前 `/api/sandbox/events` 只做 SocketIO 转发。正式接入后需要增加：

1. 根据 `session_id` 找到 Conversation。
2. 根据 `agent_id + active round` 找到 AgentRun/Message。
3. 将事件持久化到数据库。
4. 更新 Message：
   - `claude_output_delta`：追加 raw_output/content。
   - `claude_error_delta`：追加 stderr 或标记 warning。
   - `file_write`：添加 file/image/artifact element。
   - `agent_task_completed`：status=done。
   - `error`：status=error。
   - `claude_stopped`：status=stopped。
5. 通过 SocketIO 推送正式聊天事件。

建议事件名称：

```text
conversation_message_created
conversation_message_delta
conversation_message_element_added
conversation_message_status
conversation_agent_run_event
```

#### ModelConfigService

新增用户级模型配置服务：

```text
get_user_model_config(user_id)
save_user_model_config(user_id, config)
get_container_env_vars(user_id)
```

`get_container_env_vars()` 输出给 `DockerContainerManager.create_session()` 使用。没有配置时，应阻止创建沙箱会话并返回明确错误：“请先在设置中配置模型 API Key”。

#### SandboxLifecycleService

新增容器生命周期服务：

```text
touch_conversation(conversation_id)
destroy_on_conversation_delete(conversation_id)
stop_inactive_containers(older_than=24h)
ensure_running_for_conversation(conversation_id)
```

实现策略：

- 每次发送消息、收到 Agent 事件、访问文件时更新 `last_active_at`。
- 删除会话时调用 Docker stop/remove。
- 1 天无活动自动停止容器，`sandbox_status` 置为 `stopped`。
- 因 workspace 不持久化，停止后的容器重新创建时是空 workspace，前端需要提示“工作目录已随容器停止清空”。

### 4.4 容器与工作目录策略

容器内目录保留现有结构：

```text
/workspace/
  shared/
  agents/
    moderator/
    {agent_id}/
 .session/
```

当前阶段不挂载 volume，不做 workspace 持久化。保持容器内临时 `/workspace`：

- 容器运行期间可访问工作目录。
- 删除对话后容器销毁，workspace 丢失。
- 1 天无活动自动停止后 workspace 丢失。
- 后续如果需要保留关键产物，由 Agent 事件或用户操作将文件内容写入数据库的 Artifact 表。

### 4.5 多 Agent 协作实现

多 Agent 会话中必须自动加入一个内置主持 Agent。用户选择两个或两个以上普通 Agent 创建群聊时，后端自动添加主持 Agent。

推荐流程：

```text
用户消息
  -> moderator 生成结构化任务拆解 plan
  -> 后端解析 plan
  -> 按 plan 的 parallel_groups / dependencies 分发给目标 Agent
  -> 每个目标 Agent 独立执行
  -> 结果进入各自消息框
  -> 如果 plan.summary_required=true，后端再调度 moderator 生成最终总结消息
```

阶段 2 的正式链路调度放在后端实现：后端先调用容器内 `moderator` Agent 获取 JSON plan，然后由后端解析 plan、创建 AgentRun/Message、控制并行/串行执行和状态流转。容器内仍然可以同时运行多个 Agent，但容器只负责“执行指定 Agent 的任务”，不负责正式聊天的任务调度决策。

主持 Agent 必须输出结构化 JSON plan。建议格式：

```json
{
  "summary": "任务拆解摘要",
  "tasks": [
    {
      "task_id": "frontend-ui",
      "agent_id": "frontend",
      "title": "实现前端页面",
      "instruction": "...",
      "depends_on": [],
      "can_parallel": true
    },
    {
      "task_id": "integration",
      "agent_id": "reviewer",
      "title": "集成检查",
      "instruction": "...",
      "depends_on": ["frontend-ui"],
      "can_parallel": false
    }
  ],
  "parallel_groups": [
    ["frontend-ui"],
    ["integration"]
  ],
  "summary_required": true
}
```

后端调度规则：

- 先执行没有依赖的任务。
- 同一个 `parallel_groups` 内的任务可以并行。
- 后一组必须等待前一组全部 done。
- 某个任务 error/stopped 后，依赖它的任务默认不执行，并标记 skipped。
- 如果 moderator 输出的 JSON plan 解析失败，本轮直接标记为 error，并向前端提示“主持分派失败，请重试”；不降级广播给所有 worker。
- 如果 `summary_required=true`，所有可执行 worker 任务完成后，后端再次调用 `moderator`，把 worker 结果汇总给用户；如果为 `false`，本轮在 worker 全部完成后结束。

### 4.6 前端正式聊天改造

#### Dashboard.vue

需要从“HTTP + SSE mock 消息”改为“HTTP 发起 + SocketIO 接收正式消息事件”。SSE 相关逻辑从主链路移除。

改造点：

## 5. 分阶段落地计划

### 阶段 1：正式对话接入 Docker 沙箱

目标：每个正式对话创建临时容器，单 Agent 能真实调用 Claude Code，实时协议统一为 SocketIO。

任务：

- 为 Conversation 增加 sandbox 相关字段。
- 新增用户模型配置表和 Settings 后端 API。
- 创建沙箱前读取用户 Settings 模型配置并注入容器 env。
- 会话创建时调用 `DockerContainerManager.create_session()`。
- `MessageService.send_message()` 停止使用 `_mock_agent_response()`。
- 单 Agent 会话调用沙箱 direct send。
- 将沙箱事件回写到 Message。
- Dashboard 接收正式 SocketIO 消息事件并展示流式输出。
- 移除 Dashboard 主链路中的 SSE 依赖。

验收：

- 用户发送消息后，Agent 消息框实时输出 Claude Code 内容。

- raw output 默认折叠，正文展示 summary/elements。

### 阶段 2：多 Agent + 主持分派

目标：多 Agent 对话中由主持 Agent 分发任务。

已确认决策：

- 主持 Agent 固定 ID 统一使用 `moderator`。
- 主持 Agent 是系统内置预设 Agent，在 Agent 列表中可见，但不允许用户编辑，只允许查看。
- 创建多 Agent 会话时，用户只选择普通 Agent；主持 Agent 由后端自动加入，不需要也不允许用户手动勾选。
- moderator 输出结构化 JSON plan；如果 plan 解析失败，本轮直接提示“主持分派失败，请重试”，不降级广播给所有 worker。
- 如果 plan 中 `summary_required=true`，worker 任务完成后再让 moderator 做最终总结；否则 worker 完成即结束本轮。
- 多 Agent 调度在后端正式链路实现，容器只负责执行指定 Agent 的任务。

任务：

- 数据库 seed 内置主持 Agent，固定 ID 为 `moderator`。
- 主持 Agent 在 Agent 列表中只读展示，前端创建会话时不作为可勾选项。
- 多 Agent 会话自动注入主持 Agent，且避免重复加入。
- 容器创建时包含 moderator + worker agents。
- 用户消息先发给 moderator。
- moderator 输出结构化 JSON plan 后，后端解析并持久化 plan。
- 后端按 `parallel_groups` 和 `depends_on` 调度 worker Agent，支持并行和串行混合执行。
- plan 解析失败时，本轮 moderator 消息和 run 标记为 error，并通过 SocketIO 提示用户重试。
- `summary_required=true` 时，worker 全部完成后创建 moderator 总结消息并执行最终汇总。
- 每个 Agent 独立消息框流式输出。
- 支持每个 Agent 独立 done/error/stopped。

验收：

- 多 Agent 会话中至少看到 moderator 和 worker 的消息框。
- 用户创建多 Agent 会话时无需手动选择 moderator，后端会自动加入。
- moderator 不能被普通用户编辑。
- worker 可以按主持 Agent 计划并行或串行执行任务。
- 每个 Agent 的输出互不覆盖。
- plan 解析失败时不会广播给所有 worker，而是明确显示主持分派失败。
- `summary_required=true` 时能看到最终 moderator 总结；为 `false` 时不会额外生成总结。

## 6. 已确认实现约束

1. Docker workspace 当前不持久化。
2. 多 Agent 群聊自动加入数据库预设的内置主持 Agent。
3. 主持 Agent 输出结构化 plan，后端根据 plan 支持并行和串行混合调度。
4. raw output 默认折叠，正文展示 summary/elements。
5. 删除对话销毁容器；1 天无活动自动停止容器。
6. 模型/API Key 来自用户 Settings 页面保存的配置。
7. 正式聊天统一使用 SocketIO。

## 6.1 仍需在编码前细化的小问题

以下不是方向性问题，但实现前建议定具体值：

1. 内置主持 Agent 的名称和显示文案。
   - 已确认：固定 ID 使用 `moderator`；作为系统内置 Agent 在列表中可见，但只允许查看，不允许用户编辑；创建多 Agent 会话时由后端自动加入，不需要用户勾选。

2. 用户 Settings 中 API Key 是否第一版就加密存储。
   - 建议：第一版至少后端脱敏返回；如时间允许，用 `SECRET_KEY` 派生密钥做对称加密。

3. 1 天无活动停止任务由谁触发。
   - 建议：第一版在应用启动时创建后台线程，每小时扫描一次；后续可换 Celery/APScheduler。

4. 容器自动停止后用户再次打开对话是否自动重建。
   - 建议：打开对话不自动重建，发送新消息时重建，并提示旧 workspace 已清空。
