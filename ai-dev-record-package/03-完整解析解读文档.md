# 完整解析解读文档

## 1. 原始命题阶段

项目最早的背景材料保存在 `sources/original-references/`。这些 PDF 和 Markdown 草案提供了 AgentHub/WeAgent 的原始命题：构建一个多 Agent 协作平台，让用户通过聊天式交互调用不同 Agent，完成代码、网页、文档、工作流等产物。

这些材料在本包中只作为原始参考保留，不提取 PDF 全文。它们的作用是证明后续开发不是孤立功能，而是围绕一个明确的多 Agent 协作平台目标展开。

## 2. AI 协作规则先行

项目在 `docs/ai-collab/archive-schema.md` 中先定义协作记录方法：每轮 AI 对话至少形成 session，有长期价值时升级为 archive、summary、spec、skill 或 rules。

这一步很重要，因为它把“和 AI 聊天”变成了“可复用的工程资产”。从这个目录可以看到，项目成员 why、zsw、zby 分别承担不同方向，归档文件需要标记负责人，避免只留下 AI 角色名而缺少人类责任边界。

## 3. Agent Adapter 与消息流阶段

`origin/agent_adapter` 展示了第一条核心技术线：让 WeAgent 能通过统一 adapter/factory 接入 Claude Code、Codex、Mock 等 provider。

这一阶段的需求包括：

- 使用统一 `AgentAdapterFactory` 通过 provider 名称创建 adapter。
- 把原来的整段字符串返回改为标准化流式事件。
- 将 Codex JSONL 和 Claude stream-json 映射为统一 `AgentEvent`。
- 让 orchestrator 能增量广播并最终持久化 Agent 输出。
- 保留 mock fallback，确保演示和失败路径可控。
- 加入 backend 测试，避免真实网络调用成为基础验证前提。

这说明 AI 协作并没有直接跳到“大而全 runtime”，而是先建立最小可测试边界：adapter contract、normalizer、orchestrator streaming、frontend SSE consumer。

## 4. Conversation Context 阶段

第二条演进线是 conversation context。`.planning` 中的 Phase 2 明确记录了上下文系统的目标：从 WeAgent 持久化消息中构建有界 transcript，保存文件/工具/产物上下文，并通过 provider-neutral prompt assembly 注入 Claude/Codex。

这一阶段也明确了限制：不声称已经等同于 Claude/Codex 原生 session resume，不提前承诺 native hooks、background jobs、interactive choices 等能力。这类限制说明 AI 协作过程中保留了边界意识，而不是把所有未来能力都写成已完成。

## 5. Toolset Capability 阶段

`origin/feature/toolset` 是记录量最大的分支，集中体现了 AI 协作式工程推进。

它将 Skill、Tool、MCP、Plugin 抽象为同级 capability，并围绕以下问题形成计划和验证：

- capability 存入 DB，带版本、来源数据和权限声明。
- Agent 默认绑定 capability，而不是每次会话临时选择。
- capability 绑定默认 pinned version，避免隐式升级破坏复现。
- sandbox 启动时将已选 capability 投影为 `/workspace/.weagent/*`。
- Skill Markdown 可创建、编辑、导入、投影、由 Agent 修改并生成 draft。
- 外部导入必须 preview-before-confirm。
- 高风险导入和 draft publish 需要安全审查和专家 override 记录。
- npx/MCP 执行只能发生在 sandbox 容器内。
- built-in Tool 调用必须写入可审计 call record。

这一阶段的 `.planning/phases/001-toolset` 里有大量 checkpoint、UAT issue、真实环境验收指南和 PR handoff，说明 AI 参与的不只是设计，也包括验收路径、问题清单、回归检查和交接说明。

## 6. Toolset 与桌面运行时融合

`origin/combine/toolset_v1.1.0` 展示了合并与融合阶段。Phase 03 的目标是把 `origin/feature/toolset` 作为模块合入桌面端基底，同时保留 desktop sandbox/provider runtime 作为执行权威。

Phase 03 验证记录显示：

- 保留桌面端多 provider sandbox image。
- 迁入 capability 数据模型、schema、controller、service、seed logic 和 DB API。
- Agent 创建/编辑同时支持 provider selection 与 capability binding。
- 将 DB-backed capability projection 注入 sandbox。
- 保留 Skill projection、MCP runtime/list/call record 和 built-in Tool audit。
- 后端完整测试达到 `201 passed`，frontend build 和 contract tests 通过。
- Docker smoke 验证 `.weagent` projection、agent creation 和文件读取。

这部分非常适合作为“AI 协作结果经过系统验证”的证据。

## 7. Desktop Toolset Adapter 阶段

Phase 04 将工具集能力扩展到 Electron 桌面端。它不是让 Electron 直接执行工具，而是让桌面端通过同源 backend API 管理能力，执行仍留在 backend/sandbox/provider runtime。

Phase 04 验证记录显示：

- 新增桌面 `/tools` route 和 Toolset 管理页面。
- 桌面端支持 Skill/MCP/Plugin/Tool 分组、category-first navigation、导入、安全审查、provider config 管理和删除影响预览。
- Agent 创建/编辑支持 capability binding 和 pinned versions。
- Codex provider 能读取绑定 MCP 并写入 config。
- Claude provider 能把 capability bootstrap 写入 prompt files。
- backend 全量测试 `207 passed`，Web frontend build 通过，Desktop build 通过。

这说明项目从 Web 能力管理推进到桌面端可用，并保留了运行时边界。
